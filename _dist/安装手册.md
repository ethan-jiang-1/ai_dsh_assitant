# dsh-smart-assistant 手动安装手册

| | |
|---|---|
| 版本 | 0.1.13 |
| 安装包 | `dsh-smart-assistant-0.1.13.tgz`（与本手册同目录） |
| 打包日期 | 2026-11-03 |
| 验证基线 | DSH `dsh-v0.2.1-rc.2`（Node ^22.19.0 || >=24） |
| 安装前提 | pnpm `>=10.6.0`；更老的 pnpm 会以 `ERR_PNPM_ADDING_TO_ROOT` 失败 |

除唯一的运行时依赖 `yaml` 外，这个安装包是自包含的：bundle 补丁（`cordis.patch.yml`，含 `assistant` preset 的完整组合）、
编译产物（`lib/`，含浏览器端桌面面板与专家装配模块）、策展技能（`presets/assistant/skills/`）、
管理种子（`seeds/management/`）、三个 bin（`ov-doctor` / `expert-setup` / `assistant-data`）、
README。**安装器不在包里**：它是同目录下的独立资产 `bootstrap.mjs`（＋ `.sha256`），见下文「可选：安装器」。
DSH 本体一律按 peerDependencies 由宿主运行时提供，包里不带任何
`@deepseek-ai/*` 代码；唯一的 npm 依赖是 `yaml`
（安装时经 npm registry 拉取）。首次安装需要能访问 npm registry 或内网镜像；完全离线的机器请先把 yaml 预热进 pnpm store。DSH 安装时会按包里的 `engines.dsh` 检查兼容；
不满足会拒绝安装，不要用强制安装跳过它。安装与 headless 附录路径由仓库发布冒烟
（release-smoke）验证；Web UI 选择路径由 `agent-preset-ui` 探针在运行实例上验证。

## 产品是什么

产品 = **dedicated `assistant` profile 的组合**；工作区绑定在 `assistant-product.workspaceDir`（profile Config），
会话落在你的项目里，交付包落在 `<项目>/deliverables/<YYYY-MM-DD>-<slug>/`。专用 home 是部署选项，不是安装要求。
合同 = 包内 README 与仓根 `docs/product.md`。

## 〇、安装前提

- DSH `>=0.2.1-rc.2 <0.3.0-0`，Node `^22.19.0 || >=24`；不满足时 DSH 会按 `engines.dsh` 拒绝安装（本 pin 的安装门只读 `engines.dsh`/peer）。
- `pnpm >= 10.6.0` 在 PATH 上（Node 的 corepack 已启用也算）。**10.4 及更低会报 `ERR_PNPM_ADDING_TO_ROOT`，10.5 会忽略 profile 的 linker 设置**；这不是本插件的错误。
- `dsh` 在 PATH 上，`DSH_HOME` 可写。
- 首次安装需要访问 npm registry（或内网镜像）拉唯一依赖 `yaml`；之后运行不需要网络。

Windows：命令在 PowerShell 里可用；路径含空格时加引号。本手册的 `cp -R` / `nohup` 示例是 POSIX 写法，Windows 请优先改用 `assistant-data`。

## 〇之二、选运行时

同一个 bundle 装在哪种 dsh 运行时上，只影响"谁提供 dsh"，不影响安装命令：

| 运行时 | 怎么装 | 注意 |
|---|---|---|
| npm 全局 | `npm install -g @deepseek-ai/dsh`，然后用它的 `dsh` | 最常见；Node 与 pnpm 版本是主要故障源 |
| 官方 Desktop | 用 Desktop 安装包自带的命令；Plugins 页同一句话 | `desktop` profile 由 Electron 独占，普通 CLI 不能 boot/管理 |
| 源码树 | `pnpm dsh`（tsx，需先 build） | 开发/自托管；缺前端产物会启动失败 |
| Python wheel / 容器 | wheel 内置 CLI / 镜像 entrypoint | 容器是 `dsh web` 的部署包装，不是第五种运行时 |

不要在安装器里再包一层运行时：产品不拥有 launcher，也不做第二套更新。

## 一、安装（DSH 推荐：应用内 Plugins 页）

**默认：在 DSH 的 Plugins 页安装 `dsh-smart-assistant`。** 这是 DSH 的跨面安装入口：`dsh web` 与 Desktop
用同一句话；页面没有 profile 参数，装的是**当前 profile**。装完重启 profile（bundle membership 变化要重启）。

### A. 专用 custom profile `assistant`（推荐）

1. 一次性建 profile（CLI 自动化；**只用于全新 profile** —— `--from-default-profile` 是破坏性重置，
   会删掉该 profile 的依赖与用户 patch）：
   `dsh --profile assistant --from-default-profile web --dump-config`
   （`--dump-config` 不能省：不带它 launcher 会直接 boot，而不是建完就退。）
2. 启动 `dsh --profile assistant`。
3. 侧栏 **Plugins** → **Add plugin** → **Install a third-party plugin**，填 tarball 的**绝对路径**
   （如 `/path/to/dsh-smart-assistant-0.1.13.tgz`；已发布后填 `dsh-smart-assistant@0.1.13`；当前 profile = `assistant`）。
4. 启用 bundle，重启 profile；首屏选项目目录。

**顺序不能反**：Plugins 页不创建 profile，只装当前 profile；必须先有并启动 `assistant` profile，再在页面装。

### B. 当前 profile（快速试用）

1. 启动 `dsh --profile <你的 profile>`（或 `dsh web`）。
2. 侧栏 **Plugins** → **Add plugin** → **Install a third-party plugin**，填 tarball 的**绝对路径**
   （或已发布包名 / Git 地址 / 本地目录）。
3. 启用 bundle，重启 profile；首屏选项目目录。

这条路径装进当前 profile，不是 dedicated `assistant` profile；入口行/首启/交付包仍工作。

### C. CLI（自动化 / 非 GUI surface）

应用内页面不能用于自动化时，用 CLI 装；它面向 web 自动化，不能管理 Desktop。headless/SDK/ACP 没有 Plugins 页，也用 CLI 显式 profile：

```sh
dsh plugin --profile assistant add /path/to/dsh-smart-assistant-0.1.13.tgz
dsh --profile assistant --port 0
```

Desktop 不要用 CLI；用 Desktop 的 Plugins 页。装完 `--dump-config` 应看到 `assistant-product` 与 `preset-assistant`。
“装成功”有三个状态：pnpm exit 0 → dependency 写入 → `dsh.profile.bundles` 含该 bundle；只有第三个让功能存在。
CLI 装完宿主不知道，必须重启 profile；应用内装可能返回 `restart-required`。

### D. Desktop

只用 Desktop 的 **Plugins** 页安装（**Add plugin → Install a third-party plugin** 填 tarball 绝对路径）；重启应用。
Desktop 使用保留的 `desktop` profile，普通 CLI 不能 boot/管理它；
**不要写** `dsh plugin --profile desktop`。Desktop 上没有 dedicated `assistant` profile 时，产品以 Desktop 当前
profile 运行；不承诺独立 profile/专用 home。本轮未在 Desktop 真机验证。

### E. 市场（Discover，发布后可用）

DSH 没有中心化官方市场，市场是**索引源**模式：你自己加一个索引 URL，Discover 里就有这张卡片。
本仓发布后由 `pnpm market` 产出 `_dist/market/index.json`（官方 generator 生成），把整个 `_dist/market/`
目录静态托管到 https，再把 URL 加进索引：

1. 侧栏 **Plugins** → **实验性插件** 旁 **更多** → 启用 **自定义插件市场**（出厂关着；版本需与当前 DSH 配套）；
2. 重开 Plugins 页 → **Discover** → 添加索引源 URL；
3. 搜 `dsh-smart-assistant` → 选版本 → 安装（它走的是与 Plugins 页同一个 install 通道）。

索引是**声明不是签名**：卡片上的标题/作者/标签是索引的说法，装下来的字节由 manifest 决定；索引里钉的是 exact 版本，
所以"升级"= 换索引里钉住的版本再装一次。**没有索引就还没有这条路径**——先有 npm 发布，才有 market。

### 可选：安装器（自托管 / shell）

目标用户没有 DSH 经验、或需要离线/一条命令时，用**本目录下的独立资产** `bootstrap.mjs`
（与本手册、`dsh-smart-assistant-0.1.13.tgz` 同目录，附 `bootstrap.mjs.sha256`）。**它不在安装包里**，也不是 DSH 的默认
安装方式，只是 shell/自托管的安装包装：

```sh
# 校验后把它指向解开的产品包
shasum -a 256 -c bootstrap.mjs.sha256
node bootstrap.mjs --package ./package --workspace /path/to/your-project
node bootstrap.mjs --package ./package --product
node bootstrap.mjs --package ./package --stop --home ~/.dsh-smart-assistant --product
```

装好后包里没有第二个 profile 写者：默认 preset 已经随 bundle 走，安装器只负责建 profile、装包、
校验组合、起 Web。

它建/复用 `assistant` profile、装本包、校验组合，再起 Web；`--workspace` 只设一次性 `ASSISTANT_WORKSPACE`，
不写工作区绑定文件；专用 home 默认 `~/.dsh-smart-assistant`（不碰日用 `~/.dsh`）。首启选目录写 profile Config。
专用 home 是新 home：首次打开没有 provider 凭据，在 Web UI 登录/添加 API Key 后才有会话能力。

**profile 只隔离组合，不隔离数据。** 多个 profile 共用 `<DSH_HOME>/assistant` 与 `<DSH_HOME>/assistant-operating`；
要真正隔离试用，换一个独立的 `DSH_HOME`，或同时覆盖 memory/ledger/projection 的 `dataDir`。

## 二、首启与工作区

没有工作区绑定时，启动后首屏是产品开始页：**选一个项目目录**。选择后：

- 入口行校验路径、用 `workspaceRegistry.create` 登记；
- 通过 `settings.update` 把 `assistant-product.workspaceDir` 写进当前 profile patch；
- 首屏显示 `工作区 · <目录>` 与“开始一件事”；
- 之后启动从 profile Config 恢复；要换项目点“换项目”。

也可以在 profile patch 预置（团队/自动化）：

```yaml
- id: assistant-product
  config:
    workspaceDir: /path/to/your-project
```

一次性启动覆盖用环境变量 `ASSISTANT_WORKSPACE=/path/to/project`；它不替代 profile Config。
工作区**不写**工作区绑定文件，也不写 home patch。

## 三、验证安装

```sh
dsh --profile assistant --dump-config
```

输出里应能看到：

- 插件的补丁层（`dsh-smart-assistant`）；
- host 面的 `assistant-memory` 行（working folder 的四房间存储）；
- `id: preset-assistant`（`assistant` preset 的组合行）。

`default: assistant` 由 bundle patch 携带，装完即生效；用户自己选过预设（`selectedDefault`）时以用户选择为准。
这里若仍是 `standard`，先查装的包版本（当前包不该有这个读数），见「常见问题」。

## 四、让它出现在界面上

重启 `dsh --profile assistant`（浏览器刷新本身不会加载新模块），然后**硬刷新**页面（⌘⇧R / Ctrl⇧R）。之后：

- 侧栏出现 My Desk 桌面面板（记忆 / 知识页 / 技能 / 养护检查）；
- 新会话默认就是「章鱼管家」（`assistant`），它带着自己的 working folder 工作。

## 五、配置

默认值在 bundle patch；你的覆盖写当前 profile 的 patch（Settings 里的改动也落这一层）。**patch 对同一行是整份替换**，
覆盖时要把想保留的字段一起写全；完整 schema 用 `--dump-config-schema` 看。常用的几个：

| 行 | 字段 | 默认 |
|---|---|---|
| `assistant-product` | `workspaceDir`（volatile）、`onboarding` | 未绑定；`true` |
| `assistant-memory` | `dataDir`、`digestMaxBytes`、`recallLimit`、`staleResearchDays` | `<dshHome>/assistant` |
| `assistant-operating-ledger` | `dataDir`、`keepOperations`、`maxArchiveBytes` | `<dshHome>/assistant-operating`；256；256 MiB |
| `assistant-desk-projection` | `maxProjectionBytes`、`allowFixture` | 8 MiB；`false` |

密钥走环境变量或凭据服务，不写进 patch：Viki 的 key 从 `apiKeyEnv`（默认 `OPENVIKING_API_KEY`）读。

## 六、OpenViking / Viki（可选）

不装这一层，插件照常工作；Viki 面板显示未连接。要开第二记忆层：

### 1. 装 server

需要 Python 3.10+。有 `uv` 时：

```sh
uv tool install openviking==0.5.1.1
```

没有 `uv` 时用 pip/pipx 装同一版本。`uv tool install` 装不进系统目录（沙箱/受管机器常见）时，
用隔离 venv，并用该 venv 的 `openviking-server` 启动：

```sh
uv venv ~/.openviking/venv
~/.openviking/venv/bin/pip install openviking==0.5.1.1
```

server 与插件是独立进程，插件不会替你拉起它。

### 2. 写配置

`~/.openviking/ov.conf`（0600；不要提交真 key）：

```json
{
  "vlm": {
    "provider": "openai",
    "api_base": "https://your-provider.example/v1",
    "api_key": "sk-...",
    "model": "your-vlm-model"
  },
  "embedding": {
    "dense": {
      "provider": "openai",
      "api_base": "https://your-provider.example/v1",
      "api_key": "sk-...",
      "model": "your-embedding-model",
      "dimension": 1024
    }
  }
}
```

- VLM 必须支持 function calling；embedding 的 `dimension` 要与模型一致。
- 不写 `storage` 时 server 用 `~/.openviking/workspace`（持久）；不要把存储指到临时目录。
- 云端 provider：`OPENVIKING_CLOUD_ACK=1` 是显式标记；doctor 会检查 ack 与工具结果。

### 3. 起 server

```sh
nohup openviking-server --config ~/.openviking/ov.conf --port 1933 > ~/.openviking/server.log 2>&1 &
curl -s http://127.0.0.1:1933/health
```

health 绿只说明进程活着，不等于 search/commit 可用。

### 4. 装 DSH 侧插件

server 与插件是两个进程：只起 server，DSH 组合里没有 `openviking-memory-runtime` 行，doctor 会报
`OFF` / exit 2，Viki 也不会连上。装钉住的 0.5.26：

```sh
dsh plugin --profile assistant add @openviking/dsh-memory-plugin@0.5.26
```

离线或想用仓内钉存件时，把上面换成 `/path/to/dsh-memory-plugin-0.5.26.tgz`。装完
`dsh --profile assistant --dump-config` 应看到 `openviking-memory-runtime` 行。

### 5. 让 DSH 连上

在启动 `dsh --profile assistant` 的同一个 shell：

```sh
export OPENVIKING_URL=http://127.0.0.1:1933
export OPENVIKING_CAPTURE_TOOL_RESULTS=false
export OPENVIKING_CLOUD_ACK=1   # 云端 provider 才需要；本地 provider 省略
dsh --profile assistant
```

- 本机默认 `http://127.0.0.1:1933`；只有远程/非默认端口才需要设 `OPENVIKING_URL`。
- 插件对 DSH 默认会抓完整工具结果；云端 provider 下先设 `false`，除非你已配置 `captureFilters`。
- 云端 provider 必须显式 `OPENVIKING_CLOUD_ACK=1`；doctor 会检查。

### 6. 自检：ov-doctor

包内带一个只读 doctor；在装了插件的 profile 里运行（把 `<DSH_HOME>`/`web` 换成你的）：

```sh
node <DSH_HOME>/profiles/assistant/node_modules/dsh-smart-assistant/bin/ov-doctor.mjs \
  --config ~/.openviking/ov.conf
```

退出码：`0` 健康 / `1` 坏了 / `2` 可选层缺席或配置读不到。覆盖 health、config、upstream doctor、
search、composition、storage、cloud/capture、版本、config 同源与 MCP `initialize.instructions`；
commit 写探针默认 SKIP；加 `--write` 才创建 sentinel 会话并真提交（会新增一条记忆，慎用）。云端 provider 运行时，
命令前加 `OPENVIKING_CLOUD_ACK=1`，与上面的显式 ack 是同一个门。它不会打印 key。

### 7. 故障表

| 现象 | 原因与处理 |
|---|---|
| Viki 503 / 未连接 | server 没起；远程/非默认端口还需要设 `OPENVIKING_URL` 或 `assistant-viki.baseUrl`；先 `curl /health` |
| health 绿但 search 空/500 | 模型位不可达或 embedding 熔断；看 `~/.openviking/server.log` 的 provider/model/key |
| commit failed | VLM 连接/function calling/连续 user 消息兼容；看 `/api/v1/tasks` 与 server 日志 |
| 记忆重启后丢 | storage 指到了临时目录；改成持久路径并重启 |

## 七、升级与备份

**先停实例再恢复**；export 可以在实例空闲时做，import 必须在实例停止后做。插件拥有的数据在两个目录，不是代码目录。

包内 `assistant-data` 是推荐方式；它会把这两目录打成带 schema manifest 的备份，并排除
`writer.lock` / `*.tmp` 这类协调文件（否则恢复到另一台机器后，账本会把旧 host 的锁当成活锁）。恢复要求实例已停止；目标目录已存在时用 `--replace`，它把现有目录移到 `.pre-import-*` 旁路，不需要先清空：

```sh
node <DSH_HOME>/profiles/assistant/node_modules/dsh-smart-assistant/bin/assistant-data.mjs export \
  --assistant <DSH_HOME>/assistant --operating <DSH_HOME>/assistant-operating --out <备份目录>
node <DSH_HOME>/profiles/assistant/node_modules/dsh-smart-assistant/bin/assistant-data.mjs import \
  --in <备份目录> --assistant <DSH_HOME>/assistant --operating <DSH_HOME>/assistant-operating
# 已经启动过的 home：--replace 把现有两目录移到旁路再导入（不删数据、不用先清空）
node <DSH_HOME>/profiles/assistant/node_modules/dsh-smart-assistant/bin/assistant-data.mjs import --replace \
  --in <备份目录> --assistant <DSH_HOME>/assistant --operating <DSH_HOME>/assistant-operating
```

它只带这两个插件目录，不含 sessions/credentials/settings；不带 `--replace` 时 import 要求目标目录为空，含符号链接的备份会
被拒绝（备份必须是普通文件）；manifest 的 `schemaVersion` 不匹配会拒绝，不会猜着导入。

**专用 home 模式**：把命令里的 `<DSH_HOME>` 换成 `<productHome>`（默认 `~/.dsh-smart-assistant`，可选），
profile 换成 `assistant`；工作区绑定是 profile Config（`assistant-product.workspaceDir`），**不进**
`assistant-data`——换机后从首启/“换项目”重选，或改 profile patch。

手动 `cp -R` 也可以，但必须把协调文件排除在备份外：

```sh
cp -R "<DSH_HOME>/assistant" "<备份目录>/assistant"
cp -R "<DSH_HOME>/assistant-operating" "<备份目录>/assistant-operating"
rm -f "<备份目录>/assistant-operating/writer.lock" "<备份目录>/assistant-operating/"*.tmp
```

升级（仍建议串行；DSH 0.2.1 对 profile 变更有跨进程文件锁，并发会串行化，完成后用 `--dump-config` 确认）：

```sh
dsh plugin --profile assistant add /path/to/<新版本>.tgz
dsh --profile assistant --dump-config
```

`--dump-config` 仍应看到 `preset-assistant`；运行中的 Web 实例不会热替换代码，重启 `dsh` 后新版本生效。实测直接 `add` 新 tgz 会更新版本并保留
working folder/账本；若 CLI 拒绝同版本或要求先 remove，按 CLI 提示先 `remove` 再 `add`——
`remove` 不删 working folder/账本，但升级前仍建议备份。

**专用 home 模式**：home 换成 `<productHome>`（可选）；
升级前先停产品实例（安装器用 `bootstrap --stop --product`，native 直接停 `dsh --profile assistant`），升级后重启 profile。
回滚：保留上一版 tgz；`remove` 新版后 `add` 旧版；若新版引入不可读的数据格式，先恢复备份。

整 home 备份（含 sessions/credentials/settings）也可以，但不要把代码目录当数据目录。

## 八、卸载（删包，留数据）

```sh
dsh plugin --profile assistant remove dsh-smart-assistant
```

卸载后 `--dump-config` 不再提及插件，profile 的 package.json 也不留痕迹；运行中的实例重启后不再加载。
**0.2.0 之前用安装器装过**：profile patch 里可能有一段 `# Written by dsh-smart-assistant bootstrap.mjs` 的
`agent-preset-registry` 块。`remove` 不会删它；它会让 profile 继续默认 `assistant`，而 preset 定义已随包移除。
卸载后把这一段删掉；重装前也建议删掉，才会继承 bundle 的默认值。working folder
本身（`<DSH_HOME>/assistant/`）是数据不是插件：卸载不删它，弃用前自行备份。专用 home 模式用 `dsh plugin --profile assistant remove dsh-smart-assistant`；数据根是专用 home（默认
`~/.dsh-smart-assistant`，可选），卸载同样保留；工作区交付包随项目保留；工作区绑定在 profile Config（`assistant-product.workspaceDir`），不随插件备份迁移；要清就在 profile patch/Settings 里清。

装了 OpenViking 的，另停 server 并 `uv tool uninstall openviking`；`~/.openviking` 是配置/数据，
备份后再删。

## 九、headless / 自动化：profile patch

headless/SDK/ACP 没有 Plugins 页。先建 headless profile 再装包——对自定义名字，`dsh plugin` 只建 base-only profile，
没有 web-app 就起不了 Web：

```sh
dsh --profile assistant --from-default-profile headless --dump-config
dsh plugin --profile assistant add <tarball>
```

装包后五个 web-only 行（`assistant-product`、`assistant-desk-projection`、`assistant-ui-mode`、
`assistant-rooms`、`assistant-viki`）会按 `connection` 自禁用；`schedule` 不在 headless 组合里。
**不要再手写这些 disabled 行。**

只有要让 `assistant` 成为该 headless profile 的**默认 preset** 时，才需要写一条 patch：headless
模板没有 `agent-preset-registry` 行，bundle patch 的裸 `- id:` 覆盖在这里落空。打开
`<DSH_HOME>/profiles/assistant/cordis.patch.yml`，把占位 `[]` 整行替换成（或追加）下面这一块：

```yaml
- insert:
    - id: agent-preset-registry
      name: '@deepseek-ai/dsh-agent-preset-registry'
      config:
        default: assistant
```

然后 `dsh --profile assistant --dump-config` 应看到 `default: assistant` 与 `preset-assistant`。
如果你显式传了 `--preset` 或用户已选默认，可以不写这一段。用了别的 profile 名，把路径里的 `assistant` 换掉。

## 十、专家装配（可选：导入管理种子）

新 home 的默认身份已经是管理岗；管理知识种子**不会自动导入**——安装不写 working folder。
要把管理参考页按治理路径先落成 draft：

```sh
node <DSH_HOME>/profiles/assistant/node_modules/dsh-smart-assistant/bin/expert-setup.mjs \
  --data-dir <DSH_HOME>/assistant
```

- 只迁移未经改动的旧通用 SOUL；你编辑过 `SOUL.md` 就跳过。
- 种子以 `draft` 落 `knowledge/`，不进检索/摘要；在 Web UI 知识室（或手改文件）把 `draft` 改成
  `stable` 才是批准。
- 重复运行幂等；已有的 `stable`/`deprecated` 页不会被回滚。

## 十一、独立目录启动（无 git）

这是**无参 standalone** 模式（dev/demo，不是产品主路径；没有工作区绑定，profile 是 `assistant-standalone`）。专用 home 模式用
`--workspace`/`--product`（见文首），同一个 `bootstrap.mjs`。

把 tarball 解开到任意目录（不需要 `.git`、不需要本仓），用同目录的独立资产指向它：

```sh
node bootstrap.mjs --package ./package
```

前提：PATH 上有兼容的 `dsh`（或 `--dsh <命令>`）、Node 自带的 `npm`、以及 `pnpm >= 10.6.0`（脚本会在创建 home 前检查，旧版本直接报错）。脚本会：

- 在 `--home`（默认包目录旁的 `assistant-data/`）建隔离 `DSH_HOME`、workspace、agents-home、tmp；
- 用 `web` 模板建 `assistant-standalone` profile，装当前包；
- 起 `dsh --port 0`，打印 URL 与停止命令；不碰日用 `~/.dsh`。

`--home` 必须在包目录外；指向包内（含符号链接解析后）会被拒绝（数据不能混进 agent 物）。

停止：`node bootstrap.mjs --stop`（用了 `--home` 就带同一个目录）；只建不启动：`--no-start`。
搬移整个 home：先 `mv`，再对新路径跑一次 `bootstrap --home <新路径> --no-start`；脚本会重建 profile（配置/选择重置），两个数据目录保留；profile manifest 损坏/只写了一半也会走同一修复。不要只 `mv` 后直接启动。
离线：`--offline` 让 pnpm 走离线；前提是 pnpm/Corepack 本身已在机器上、`yaml` 已在 store/缓存。Corepack 首次下载 pnpm 仍需网络；冷缓存会明确失败。
首次模型：新 home 没有凭据，在 Web UI 里配置 provider，或按你的部署方式提供。
Windows：`dsh`/`npm` 的 `.cmd` shim 与进程树语义已做代码级加固，但本轮未在真 Windows 上跑过；优先用 WSL，或直接把 tarball 装进目标 profile。

## 十二、安全

- **token URL 不进截图/日志**：`dsh web` 打印的根 URL 带一次性 token；排障贴日志前先删掉查询串。
- **不要 wildcard bind**：`--host 0.0.0.0` 会被拒绝；远程访问用一个具体地址 ＋ 反向代理 ＋ TLS。
- **代理要显式信任**：`--public-url` 只做广告、不授予信任；反代的 authority 必须给 `--trusted-host`，
  否则请求不被信任。TLS 证书对必须成对，启动失败不回落 HTTP。
- **凭据不进 patch**：API key / OpenViking key 走 env 或凭证服务，不写进 profile patch（会跟着配置一起被备份/分享）。
- **安装器资产要校验**：`bootstrap.mjs` 是独立发布资产，用同目录的 `.sha256` 校验后再运行。
- **卸载不删数据**：`assistant/`、`assistant-operating/`、`cache/assistant/` 留在盘上；要走就自己删。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 刷新后什么都没出现 | 浏览器刷新不加载新模块：重启 `dsh --profile assistant`，再硬刷新页面 |
| Web UI 里没有章鱼管家 | 先确认 `preset-assistant` 在组合里、装的是当前包；重启并硬刷新；仍没有就按第五节查配置，并记录界面缺口 |
| 升级后数据在哪 | 仍在 `<DSH_HOME>/assistant` 与 `assistant-operating`；专用 home 模式在 `<productHome>` 下；`remove` 不删；升级前先备份 |
| 安装器与 native 有什么区别 | 安装器（A）帮你建 `assistant` profile、装包、起 Web；native（B）用 DSH 三步达到同一 profile；两者的工作区都在首启选，写 profile Config |
| 首跑停在登录/要求 API Key | 专用 home 是新的，没有 provider 凭据；在 Web UI 登录/配置后再用，不是装坏 |
| headless 组合里多一条 `assistant-product` pending | bundle patch 的 self-disable 未生效（旧包/被 profile 覆盖）；升级当前 tarball，或在 profile 层显式 `disabled: true` 双保险 |
| 工作区交付包在哪 | `<工作区>/deliverables/<YYYY-MM-DD>-<slug>/`（README 四段 + 交付物 + `present`）；不复制会话日志 |
| 备份怎么恢复 | 用 `assistant-data import`；已启动过的 home 加 `--replace`（现有目录移到旁路，不用清空）；它按 manifest 的 schemaVersion 拒绝不兼容备份 |
| 产品启动要 dsh 吗 | 要，PATH 上有兼容 `dsh` 或传 `--dsh`；没有 dsh 的便携包是另一个产品，不在本手册范围 |
| 独立启动的数据在哪 | 默认包目录旁的 `assistant-data/`（可用 `--home` 换）；它不写日用 `~/.dsh` |
| DSH 版本不兼容 | 安装会被 `engines.dsh` 拒绝；升级 DSH 或换兼容的包版本，不要强制绕过 |
| 管理种子怎么导入 | 默认身份已是管理岗；种子用 `bin/expert-setup.mjs` 显式导入为 draft，不会自动进检索 |
| 想确认装了什么版本 | `dsh plugin --profile assistant list`，或看本手册表头的版本号 |
| 安装时要联网吗 | 是，首次安装要从 registry 拉唯一依赖 `yaml`；其余全部由宿主 DSH 提供。离线先预热 pnpm store 或指向内网镜像 |
| 安装报 ERR_PNPM_ADDING_TO_ROOT | pnpm 太旧；升到 `>=10.6.0`（10.5 还会忽略 profile 的 linker 设置） |
| 安装报 pnpm was not found | PATH 上没有 pnpm；安装 pnpm，或在 Node 22 上启用 corepack |
| 恢复后账本写不进去 | 备份里带了旧机器的 `writer.lock`；用 `assistant-data import`（会剔除），或手工删目标目录的 `writer.lock` 后重试 |
| 试用的 profile 污染了日常记忆 | profile 不隔离数据；改用独立 `DSH_HOME`，或同时覆盖 memory/ledger/projection 三个 `dataDir` |
