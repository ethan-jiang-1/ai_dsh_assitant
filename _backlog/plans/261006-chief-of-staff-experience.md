# 推敲：一把手的总助——用户体验重设计

> 立卡：2026-10-06 ｜ 状态：推敲中｜毕业门判断 = 该做（用户体验有严重问题：打开后不痛不痒，产品没有主动为用户做事）｜下一步 = 按本卡的体验弧线分阶段实施，每阶段可独立验收

## 核心问题

用户说的不是 UI 布局——是**产品打开后让不让你觉得它有用**。现在的体验：

```
打开 → 空白聊天框 → 不知道干嘛 → 自己想说什么 → 回复在聊天流里 → 关掉 → 下次打开还是空白
```

研究材料诊断（定位卡三诊 + 中国 SME 画像 + CEO 时间研究）：

1. **首屏价值错配**——第一屏是空聊天框，不是「你的经营状态」
2. **没有主动价值**——产品不为你做事，等你问它才动；总助应该你到了它已经把事情准备好了
3. **没有跟进闭环**——拍完的事没人盯，流失在聊天流里；总助的核心价值就是「你拍板，它盯到闭环」
4. **没有节律**——没有「每天早上来看一眼」的理由；总助应该创造「每周一坐 15 分钟」的习惯

**一句话：用户不应该「使用」一个工具——用户应该「拥有」一个随员。**

## 目标体验（从定位研究提炼）

### 角色定位
**一把手的总助**——不是聊天机器人，不是搜索引擎，是一个「替你盯住、只把该你拍板的递上来」的随员。

### 三层价值（按交付时间排序）
| 层 | 承诺 | 何时兑现 | 对应体验 |
|---|---|---|---|
| **B 军师** | 把难事拆成带行动表的处理单 | 第 1 天 | 丢一个问题 → 回来一份带选项和缺数的处理单 |
| **A 随员** | 记得你的公司、盯着你批过的事到日期 | 第 1 周 | 早上打开 → 到期的事提醒你 → 拍完 → 它跟进 |
| **C 分身** | 越用越像你 | 第 30 天起 | 你不用教它——它已经知道你的偏好和上下文 |

### 三处任务来源（用户不需要凭空生成任务）
| 来源 | 机制 | 用户感受 |
|---|---|---|
| **它先开口** | 到期驱动晨报：行动表 due、缺的数、待拍板项 | 「它替我记着呢」 |
| **它主动搭台** | 访谈式 intake：它问你答，15 分钟建公司卡 | 「它懂我想做什么」 |
| **你丢的东西有落点** | 报价单 → 知识室草稿 + 回执 | 「我丢进去的东西不会丢」 |

### 换位节律
CEO 与总助的自然关系不是聊天对象——是**「每周一坐 15 分钟的随员」+「遇事立刻问的军师」**。产品应该让用户感受到这两种节律，而不是要求用户把它当聊天工具。

## 体验弧线（从 demo walk + 外部 UX 模式研究提炼）

### Day-0：第一次打开
```
用户打开 → 看到的是一份待办简报（不是空聊天框）
         → 或者 intake 问答（它先开口：你最近拍过什么？）
         → 15 分钟内交出第一份处理单 + 落一个回访 schedule
         → 用户离开时知道：「下次打开，这里会有东西等着我」
```

### Day 1-N：日常使用
```
用户打开 → 晨报：到期的事、缺的数、待拍板项
         → 处理（拍板/回复/填数）→ 桌面更新
         → 关掉（不需要盯着）
下次打开 → 上次拍的有了进展或到期 → 继续拍
```

### 每周节律
```
周一早上 → 晨报（上周发生什么 + 本周到期 + 缺的数）
周中     → 遇事问（军师模式：丢问题 → 拿处理单）
周五     → 盘回款和下周资金 → 记录到桌面
```

## 现在有什么 vs 缺什么

| 能力 | 状态 | 差距 |
|---|---|---|
| 它先问（intake） | ✅ 已落地 | 缺：简报交付后的收尾节律句 |
| 处理单（拆解+选项+缺数） | ✅ 已落地 | 缺：打开第一眼就该看到，不是藏在聊天流里 |
| 到期排程 | ✅ 已落地（schedule_create） | 缺：到期投递的简报体验（不只是「你有一件事到期」） |
| 审批内联 | ✅ 已落地 | 缺：在第一屏就能看到并操作 |
| 晨报（打开即见） | ❌ **未落地** | 这才是核心 UX 缺口——打开的第一眼应该是「今天的事」 |
| 知识积累回显 | 部分 | 缺：让用户感受到「它记住了」的体验 |

## 分阶段实施

### 阶段 1：晨报——打开即见（最核心的 UX 缺口）
**做什么**：当用户打开产品、会话为空白或刚创建时，助手第一条消息不是等用户问——而是**主动呈报桌面上的当前状态**（到期的事/要拍的/缺的数），格式是一份简短简报，不是零散文本。
**怎么做**：不需要新机制——`morning-brief` 技能已经会做简报，需要的是**触发时机**：在空白会话的首条消息（或会话创建时）自动触发，而不是等用户说「给我晨报」。
**验收**：用户打开 → 不需要打字 → 第一条消息就是简报（即使桌面为空也说「桌面是空的，说一件事开始」）。

### 阶段 2：跟进闭环——拍完的事它盯着
**做什么**：拍板一个决策后，`schedule_create` 自动排一个复查（已有的 morning-brief 机制扩展），到期投递时展示「你拍了这个、到期了、现在什么状态」。用户不需要记——它盯。
**怎么做**：first-conversation 技能在处理单交付后**同回合**创建 schedule（已实现）；到期投递后 morning-brief 技能**读桌面并汇报进展**（不是「你有一件事到期」而是「你上周拍了这个、现在的状态是…」）。
**验收**：用户拍完 → 关掉 → 三天后打开 → 看到跟进简报（不是空白）。

### 阶段 3：知识积累——「它记得我」
**做什么**：用户提供的每条信息（公司事实、偏好、决定）在后续对话中被**引用**（「你上次说过…」），让用户感受到产品在学习。
**怎么做**：这不需要新机制——记忆/知识房间已经有数据。需要的是 **persona 级别的指令**：在回答中主动引用已有记忆（不是每次都从零开始）。
**验收**：用户第二轮对话时，助手的回答里引用了第一轮提供的信息（不需要用户重复）。

### 阶段 4：体验打磨
**做什么**：基于阶段 1-3 的真用读数，打磨体验细节（简报的格式/频率/语气、处理单的展示、审批的时机）。

## 约束与边界

- **vendor 边界内做**——不改变 vendor 壳的布局，改的是壳里的**内容和行为**
- **不做 IM / 不接外部数据源**——只用会话内提供的本地资料
- **v1 晨报不承诺新信息**——承诺「你批过的事推到该发生的那天」
- **不伪造真实经营**——示例标注 simulated，真账面需要真数据

## 输掉的方案

1. **改 UI 布局**——tab 面板视图切换是壳层变化，不是体验变化；用户要的是「产品为我做事」，不是「多了个面板」
2. **等真人回访**——真人不可用不阻塞原型（公开案例/模拟验证推进）
3. **一次做全部**——每阶段独立可验收，不做大爆炸重构

## 毕业门

问题/方案/验收齐全 + 每阶段有真模型走查证据 + 体验改善有真人可感的对照（不是只有 spec 绿）。
