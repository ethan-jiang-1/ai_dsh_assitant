> 一文件一张卡：**`YYMMDD-<slug>.md`**（六位日期 = 立卡日，归档后文件名排序即日期流；slug 用
> kebab-case）。形成毕业判断（该做 / 已裁决延后 / 否决 / 消化）时 `git mv` 到
> [`../_done/_closed_plans/`](../_done/_closed_plans/)，保留推敲正文，状态行补去向指针。
> 未裁决但被显式搁置的卡进 `_suspended_plans/`，暂停不是毕业；完整边界见规矩手册。
> 规矩手册 = [`../README.md`](../README.md)。
>
> **活跃清单**（下表）= 本目录的名册；目录树本身仍是**位置即状态**的真相（卡在不在，树说了算）。
> 名册与树的互查由 `backlog-liveness` 门禁双向把守（2026-10-02 借鉴自 ai_dsh_loop_advisor：
> 名册会漂移的老问题，靠"有门禁看守的名册"解决——notes/ 不设索引是因为那里没有这门禁，两者不矛盾）。
> 毕业判断看各卡状态行。
>
> **毕业了就得走**：`状态` 是**推敲**态，完成判断在 `毕业门` 字段——一旦它写 `已过`，卡已到站，
> 迁移只是记账残尾。`backlog: graduated plans leave the active shelf` 门禁（2026-10-08 补，见
> [治理 note](../../notes/implemented/2026-10-02-backlog-governance-borrow.md)）会点名滞留者，
> 因为 liveness 只能证明卡**活着**，看不见"毕业了没走"。
> **人待不是完成词**：`该做，四片全交付` + `剩毕业门最后一环：用户终验` 仍是活跃卡——
> 四门最后一环没走完前不得归档，门禁也不逼你谎报。

## 卡片模板

需求链和验证链是两种不同的思考方式：先把问题、价值、范围和取舍说清楚，再由验证链把已经确认
的行为翻译成可观察的验收判据。验收不能反向替需求做决定；若判据暴露意图歧义，回到需求链确认。

需求卡的模板只记录需求判断材料；需求确认后，按 [验证设计方法](../playbooks_plan_and_validate/validation-design.md)
把验收矩阵写进同一张 plan 专设的 `## 验收矩阵` 小节——毕业门只放四门判据并引用矩阵，不另建验收卡。

```markdown
# 推敲：<标题>

> 立卡：YYYY-MM-DD ｜ 状态：推敲中｜毕业门判断 = <待定/该做/待触发/待用户判触发（🔒）/倾向放弃/…>｜下一步 = <动作或触发>

## 背景 / 触发
为什么推敲这个：问题、观察、出处（会话/Note/走查）。

## 已知与未决
已核实的事实（带出处）；四问各自的开放点（该不该 / 何时 / 次序 / 放弃）。
调研类卡补三字段：**待答问题 / 待跑实验** + **喂给谁**（结论将喂给哪个决定）。

## 候选与取舍
候选方向 × 各自代价；为什么 X 不是 Y（备选只记录、不编造）。

## 毕业门
四门各自的满足条件；缺什么证据才能判。
```

## 状态行规则

首部 12 行内必须有 `状态：` 行且写明毕业门判断——**每张卡自带户口**，防挂死稿。

## 调研卡形态规范（原 notes/research 规范并入，2026-09-28）

- **一手引证**：承重结论后跟来源 URL / 包名；二手转述不算数，跟到源头。
- **证据分级**：[affordance]（源码/接口可指认）/ [documented]（官方文档载明）/ [observed]（社区观察，注明出处）。
- **版本基线**：提到的每个包写明查证时的版本或 commit 日期。
- **承重结论内联自足**：只读本文即可成立。
- **普查底稿亲验**：进文前的承重主张由委托方复核（AI 检索结果不作最终证据）。
