# 推敲：Viki 的内容面——可枚举、可读、可删、冲突并排（B 卡：P1）

> 立卡：2026-10-19 ｜ 状态：等人拍板 ｜ 类型：Feature ｜ 可关闭：否 ｜ 毕业：做现在（P1，A 卡之后）｜ 下一步 = 本人确认"越界整批清除"的口径（Q1）

> **依赖：** A 卡（[维护面收口](261019-self-update-lanes.md)）的面骨架复用；依据档 [self-update/261019-self-update-lanes](../research/self-update/261019-self-update-lanes.md) §5.2（实测）/§5.3（冲突判据）。

**问题与期望结果：** Viki 的记忆今天**没有读者也没有写者**——`ov-shield` 只挡了它的工具面与技能面，抽取物仍然自动进每轮画像/召回块；人能看见它的唯一方式是"觉得它记错了"。真代价付过一次：真机往返里助手主动指出长期记忆压着**另一家公司的 14 条底子**（[pin note](../../../notes/implemented/2026-10-19-openviking-pin-catch-up.md) 遗留节）。要的是：**能列出它记得什么、能读正文、能一条一条删（删得回来）、两条矛盾时能并排看见并指定以哪条为准**。
**当前情况：** 依据档 §5.2 的实测把"不可控"这个前提**推翻**了：server 0.4.22 的 `fs/ls?recursive` / `content/read` / `DELETE /api/v1/fs` / `snapshot/commit|diff|restore` 全现成，抽取物是 `viking://user/<space>/memories/{profile.md,preferences,entities,events}` 下的**文件**；注入面只读其中 `profile.md` + `preferences/` + `entities/`（vendor `shared/profile-inject.mjs`）。缺的是调用者与面，不是能力。本机 dev 工作区只有 `identity.md`/`soul.md` 两条模板，**那 14 条不在其中**（在另一份工作区/宿主目录，需一次性核清）。
**下一步：** 本人确认 Q1（越界整批清除）后开工 B1；B2 的删除面与 A2 的直写车道同形状，可并行。

| # | 项 | 状态 |

## 方案与取舍

| 片 | 做什么 | 要点 |
|---|---|---|
| **B1 可枚举 + 可读** | 宿主只读路由把 `memories` 树投影成条目（uri / 分类 / 标题 / 摘要 / mtime / 正文）；面板逐条可读 | 复用 A 卡的面骨架；正文按需取（`content/read`），列表只取 `fs/ls` 的 `abstract` |
| **B2 逐条删（带备份）** | 删除 = 先 `snapshot/commit` → `fs DELETE` → 回执；确认弹窗列出"谁引用它" | 引用证明：知识页 `sources`、记忆 `supersedes`/`supersededBy`、线索指针；被引用则拒绝并列出 |
| **B3 冲突并排** | 两条矛盾时并排展示 + "以哪条为准"；点完 = 退役另一条（带备份） | 与房间侧 §5.3 三段判据同一套语义：取代机器可判、冲突人裁、退役删除带证明 |
| **B4 存量清理** | 扫另一份工作区，按"越界"整批清除 14 条，出清理回执（清了什么、备份在哪） | 一次性的；清除前把该工作区的 memories 树 snapshot 一份 |

**做法取舍：**

- **不做候选层/事先审批**：外部没人这么做（依据档 §四 结论 1），且内容本来就可枚举可删（§5.2）——套队列是把可控当不可控。**采纳**"列表 + 并排 + 删 + 备份"。
- **不做逐条挑 14 条**：逐条挑=逼人读别家经营数据；越界是 scope 错误，不是值错误（§5.3），整批清 + 留备份可回滚。
- **不做"把 Viki 灌进房间"**：抽取质量不足以当权威（本次会话标题把上下文误当事实就是新反证）；房间仍是唯一权威，Viki 是情景层。
- **不做 `profile.md` 掐中间那一层改造**：先把可读可删做出来，超预算截断的行为留给真机读数决定。

## 验收标准

| # | 判据 | 断言目标 |
|---|---|---|
| 1 | 列表 = server 真值 | 面板条目数 == `fs/ls?recursive=true` 的叶子数（spec 用 3 条 fixture；不读本地拷贝） |
| 2 | 正文能读全 | 点开读 `content/read` 原样正文（≥2000 字不截断；截断时明确标注） |
| 3 | 删除可回滚 | 删一条 → `snapshot/restore` 后 content hash 与原文件相等（spec 断言 hash 相等） |
| 4 | 删除有引用证明 | 被知识 `sources`/记忆指针引用时删除被拒并列出引用者（负例 spec） |
| 5 | 冲突并排 | 两条矛盾条目并排可见；指定"以 A 为准"后 B 被退役且 A 保留（spec 断言状态与文件存在性） |
| 6 | 存量清理可审计 | B4 后 `fs/ls memories` 与 `stats/memories` 双读数都不含旧公司实体；清理回执记录清了几条、备份路径 |
| 7 | 零模型回合 | 列表/读正文/删除全走宿主路由，探针断言无会话、无模型回合 |
| 8 | 收尾 | `pnpm typecheck && pnpm test && pnpm verify` 绿；动 client 先 `pnpm build` + `pnpm shots`；动 vendor 插件则 `pnpm release-smoke` |

## 关闭条件

B1–B4 落地且上表 1–8 有真证据；那 14 条在两处读数里都消失且备份可回滚；本人在真机上确认"能列出、能读、能删、删得回来"；注入面不再有**无出处**的旧公司事实（可在 A3 收据或摘要里复核）；结论与去向按[关闭条件](../README.md#关闭条件)交接后归档。
