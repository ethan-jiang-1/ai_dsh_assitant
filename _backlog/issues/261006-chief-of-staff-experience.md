# 推敲：一把手的总助——用户体验重设计

> 立卡：2026-10-06 ｜ 状态：推敲中 ｜ 可关闭：否

**问题与期望结果：** 用户反馈原桌面看不清到底要做什么，使 CEO 无所适从；这是已得到的体验反馈，具体布局根因尚无任务观察验证。打开产品应先进入总助桌面；让一把手看清完整经营事项、各自为什么有轻重、可选的下一步和依据，并能自己选择处理哪件事。桌面发起某件事的对话后，助手追问或等本人补充时留在对话；只有该事项更新成功读回后才回到桌面，显示同一事项的新状态。界面应利用可用空间组织全貌和所选事项，不把所有信息堆在一列或一张大卡里。

**外部结果三要素：** 触发＝打开/重载产品，或从桌面选择、交代、处理一件事；用户得到＝可以扫视和选择的事项全貌、有依据的建议、所选事项的详情与对话、读回后可核对的结果；完成条件＝本轮交出对照现状的需求、可行性判断与逐项验收，不改产品代码，不以卡片写完替代产品终验。

**当前情况：** 仓内已有 root-scoped 全局桌面面板、决定/行动/缺口数据、会话内 view 偏好和部分对话入口；全局面板状态初始为 Conversation，桌面并非冷启动默认。桌面从最近会话工作区寻找一份快照；面板动作使用最新会话或传入会话，没有可靠地绑定所选事项。时间戳轮询可解除 pending，但没有自动返回全局桌面的路径。具体限制见下方现状对照；统一账本由 [CEO 持续助理卡](../_archive/settled_issues/261008-ceo-operating-loop.md) 拥有。

**已确认需求：** 用户选择主区桌面作为产品入口（包括冷启动）；事项全貌按有依据的优先级形成推荐列表，CEO 可以自己选择，证据不足时标为未能判断并让 CEO 选择；单一权威经营账本可汇入多个会话的事项并保留来源；从桌面处理事项后，只有对应事项成功更新并读回才自动返回桌面；新环境从一件眼前要处理的事开始，不以完整公司画像/固定三问为门槛；三行口语播报暂为体验假设，须看具体界面后判断；界面随空间响应，宽屏支持列表与所选事项详情，窄屏一次聚焦一个层级。

**未决问题：** 全局主区面板能否在当前 pin 插件边界内可靠成为冷启动默认并在重启恢复；无会话时如何创建/绑定首次事项对话；跨会话事项如何并入权威账本且避免错并/冲突覆盖；推荐优先级依据在现有输入边界内是否足够；界面方案是否真正让人一眼知道做什么。以上是可行性与体验待验证项，不预设一定能做或一定不可做。

**下一步：** 公开 API 的静态路径已核清；依下方 P1–P4 补生命周期/账本协议的缺口，用代表性多事项资料的隔离原型比较信息层级和响应式呈现，再依逐项验收形成实现结论。原型未运行，当前不授权改产品代码。

## 已知与未决

### 已确认的用户结果与原要求的承接

| 编号 | 当前要求 | 与旧要求的关系 |
|---|---|---|
| R1 | 冷启动、重载/再次打开都进入全局总助桌面，不依赖正在打开的 Session；不先发“你好” | 保留“第一眼是内容不是空框”，把主区入口与会话内默认 view 分开 |
| R2 | 看完整事项列表、有依据的轻重/建议/下一步；CEO 能选择任一事项，证据不足时展示未知、缺口并帮助选择 | 不用三条摘要或一个推荐卡代替全貌；“完整”指本经营账本内已接收事项，不指外部世界全部事情 |
| R3 | 宽屏＝列表与所选事项详情并看；窄屏＝列表→详情→返回，一次一个层级；保留所选事项 | “三行口语播报”是待比较的呈现假设，不是不可变版式；不靠堆图表或计数证明价值 |
| R4 | 从桌面处理明确事项时进入对应对话；助手追问、等本人输入或回合未完时留在对话；对应事项成功读回后才自动回桌面 | 用户已明确细化旧“说完话主区仍在桌面”：不是禁止对话，也不是任何一轮结束就切回 |
| R5 | 无业务数据时直接交代一件眼前的事；不先完成公司画像或固定三问 | 历史 Day-0 访谈脚本不再是必经流程；确实需要的信息在该事项中补 |
| R6 | 一个权威经营账本接收多个 Session 输入，事项保留来源 Session/原始记录；返回仍是同一事项及其最新已确认状态 | 账本和来源规则由 [持续助理卡](../_archive/settled_issues/261008-ceo-operating-loop.md#统一经营账本与多会话输入已确认)拥有，本卡消费它们，不把最近会话文件当全量 |
| R7 | 拍板记录保持中文本人口吻；重载不用重讲已有背景，不凭空创建业务对话或调用模型 | 保留旧“拍板是本人的话”“它记得我”；长期跟踪和经验迁移的价值不由一次 UI 重载验收 |

提醒筛选、主动建议、进展/完成依据和条件经验由 [持续助理结论与下游申请](../_archive/settled_issues/261008-ceo-operating-loop.md#业务选择与下游交接判断) 承接：回款情景/更新权限已确认，Host 候选与 V1–V9 已形成，业务运行未验证。本卡消费该方案的身份/来源/操作读回语义；它尚未实现，不解除本卡 A2/A4/A6 的证据缺口。

### 历史失败与本轮取舍

1. **自动发“你好”不是主动经营内容。** 历史 fresh 判定按新会话，导致重载重发、会话增殖和高 token；已有业务数据也被模型猜成新环境。确定性读取已知内容保留，自动问候/造对话退役，不复建。
2. **藏 composer 不能把聊天变桌面。** 历史 CSS 残留导致无法输入；DOM 中存在输入框曾被误判为可输入。不能通过隐藏平台输入面实现形态迁移，输入可见与真输入必须单独验证。
3. **tab、主区注册和口语文案只解决了一部分。** 全局面板是可用承载，但没有解决默认选择、全量数据、事项路由和成功返回；“有卡片/能点”不再作为整体体验通过信号。
4. **D7 限制曾被扩大解释。** 它限制的是会话内默认 view/blank 贡献；不能由此推出独立全局主区默认不可做。反过来，有 `selectPanel` 也不能跳过组合、初始化、注销和导航验证。
5. **局部走查被读成价值完成。** 历史“交付”主要有分支、文案、排程与一次现场；易失截图、未检查的重载副作用、未完成的用户判断没有补齐。原记录保留，不改写成通过。

历史现场和失败依据继续见 [开屏卡历史观察](261007-opening-brief-and-rhythm.md#历史观察与实施记录)及本卡文末。

## 约束

- 只在本插件边界内，不改 vendor、不升级 pin 来绕过问题；不做 IM、不接外部数据源。
- 一个权威账本不等于把 Session 日志或四个房间合并。原始来源、事实/经验及 UI 投影的职责仍需区分；不另造第二份可写经营真相。
- 本轮只推敲并修改文档，不启动服务、不做生产原型或实现；未来有界原型按 [补证据方法](../methods/requirements-probes.md) 的隔离分支与回收要求处理。
- 不在本卡设计完整提醒算法、组织协作、外部执行、长期学习或数据接入；不把多个经营账本/公司切换当作已确认功能。
- 三行文案、固定分区数、固定像素断点不是用户已定答案；具体选择须有呈现比较。代码切片获授权后独立提交、自测、verify。

## 方案与可行性

| 真正比较过的路径 | 判断、代价与验证边界 |
|---|---|
| 会话内 view 作为默认桌面 | 当前 pin 的 blank 渲染和默认选择仍有限制；旧偏好写入未交付。不是本轮推荐主路径，相关上游触发只适用于此路径 |
| 独立全局 `main` 面板作为主入口，Conversation 作为事项处理面 | **推荐继续验证的技术路径，不是已可交付结论。** 当前有注册和 `ILayout.selectPanel`，无需 Session 绑定；工作区 startup restore 使用 `preserve`，不主动切掉全局面板。仍须验证注册后选中、卸载/重挂、冷启动/重载；当前会话被归档等 `clearMain` 路径会选回 Conversation，须纳入反例，不能循环抢焦点 |
| 继续让 CEO 手动点桌面、或自动问候后再找桌面 | 手动入口可留作显式导航，但不满足 R1；auto-send 已有失败证据，不作为默认替代或临时补丁 |
| 一个推荐事项/三行摘要替代全貌 | 认知负担小但会隐藏未选事项，违反 R2。可作为列表上方的简报候选，不能封死 CEO 自选 |
| 宽屏列表＋详情，窄屏列表→详情→返回 | 用户已确认的层级；插件可在自己的主区布局。代价是选中态、滚动位置和实际剩余宽度的响应。分界不能只看窗口宽度：[平台外框](../../vendor/dsh/packages/client/ui-layout/src/client/AppFrame.tsx#L129-L174)还会扣左栏/右栏；[列宽规则](../../vendor/dsh/packages/client/ui-layout/src/client/columns.ts#L52-L58)不保证桌面内部的两栏始终放得下 |
| 最近 Session 的快照当经营账本 | 维持现状容易，但不满足多会话完整性与来源。共享 `dataDir` 是已有持久承载；账本身份、写入权、并入/冲突和版本规则仍需 261008 定义，不能把“能写文件”称为账本已可用 |

**可行性结论分层：** 主区入口、面板选择、Session 创建/保有、工作区导航和 prompt 提交都有公开 API 路径；当前插件尚未把这些连成事项导航，尤其未声明使用 `uiWorkspace`。无活动 Session 不妨碍显示全局面板，但工作区文件读取仍需 Session 地址，不能把当前 `workspaceFiles` 当任意全局读文件接口。共享账本的 Host 读写路径、权限与多写者规则需要插件内设计。空间布局可在面板内试验；优先级是否有足够事实、模型能否正确更新、用户是否觉得清楚，均未由 API 证明。

## 验收标准

以下把确认结果变成下游可执行验收；不是本轮执行报告。原五项分别由 A1/A2、A4–A6、A8、A1/A7/A8、A9 承接；R4 的变化与三行版式降为假设来自本轮用户确认，不是为迁就现有实现改绿。证据路线以 [测试证据地图](../../docs/testing.md) 为准。

### 固定输入、独立预期与状态读法

- **S0**：无业务数据、无已有 Session；区分平台初始化的空白 Session 与业务对话。**S1**：已有账本、无打开 Session；**S2**：同一账本已有多个 Session，最近 Session 无关或属于另一工作区。
- **S3（明确标注的模拟资料）**：账本含 7 件在办事项，其中 4 件等拍板、1 件已到期未完成、1 件有跨事项依赖、1 件证据不足；另放 1 件已完成事项供核对历史，标题包含长中文。独立列出期望事项集合、来源与状态；不能从页面渲染结果反推“应有集合”。7 件用于超过当前三条截断，不是产品数量上限。
- **S4**：Session 甲/乙同一事项的新旧进展、同名但不同事项、互相冲突的日期、无关事项刷新；使用可识别来源与不同修订。账本并入预期须先由 261008 明确；未明确前相关行是证据阻断，不让测试自己发明答案。
- **S5**：同一资料中写明关键期限/影响/依赖及出处，再移除证据或加入冲突；预先列可支持、可反对与尚不支持的主张，不预置一套未经确认的永久权重。比较关键条件变化前后的建议及解释，不能原样复制已失效理由。排序不靠输出里有没有“建议”判绿：已知依据须可追，未知不能装成确定；建议轻重是否合理仍由本人判断。
- 每次运行记录源码/构建基线、pin、profile/home/workspace、预置 Session 数和账本修订、实际命令/场景。先验行为期望与之后观察分别记录；模拟、模型观察、用户判断不混写。
- **成功的含义**：本卡自动返回指此次事项处理已经结束、对应更新成功读回；不等于整件经营事项已完成。一次补数/延期/拍板后，事项可能仍在跟踪，完成状态及后续提醒继续由 261008 的业务规则决定。

## 历史讨论与实施记录

以下保留原设计、实施安排与失败路径；历史勾选和机制说法只代表当时记录，当前完成状态和接手行动以上方摘要、验收及分支为准。尤其“list 槽”说法不适用于当前 `main` keyed slot；root-scoped 表示不依赖 Session，不等于已被冷启动选中。历史“dashboard → 对话已交付”只涵盖通用入口，不代表事项会话绑定已完成。

### 走偏了什么（诚实复盘）

定位卡 18 轮讨论出了一个完整的体验重设计——**standing briefing desk**（打开=桌面，有内容等着你）。但实际执行偏成了**reactive chat + patches**（在聊天壳里加视图/技能/面板）。

| 历史设计 | 实际落地 | 差距 |
|---|---|---|
| 首开即晨报（打开=简报等着你） | 打开=空聊天框+首开条 | 晨报技能存在但需要用户先发消息 |
| 桌面=主对象（会话=动作） | 桌面=一个 tab（不是默认） | 视图 tab 不等于形态迁移 |
| 任务从三处来（它先开口/搭台/有落点） | 只有「你丢的有落点」部分工作 | 它先开口=用户先说话助手才转问 |
| 每周一坐 15 分钟 | 没有节律机制 | 无主动推送/无习惯回路 |

偏差根源：**我在做「技术能力落地」而不是「体验设计落地」**——能力是能不能做，体验是用户感受到什么。这两个是不同的事。

### 历史讨论的核心设计（要召回的东西）

#### 从外部 UX 模式研究（Clay/Motion/NotebookLM/Dex）
**核心模式：聊天是对主对象的查询与操作层，不是产品的主界面。**
- Clay：首屏内容来自自动整合的既有数据，不来自用户输入
- Motion/Reclaim：主对象=日历/任务 dashboard，聊天排在主对象之后
- NotebookLM：Featured/sample 内容是零数据首跑的正规解

#### 从定位卡 18 轮的定调
1. **首屏价值倒转**：首开即晨报（不是空白聊天）——产品形态从 reactive chat 变 standing briefing desk
2. **桌面为主对象**：会话降为桌面上的一种动作（像 issue 上的评论）
3. **任务从三处来**：它先开口 / 它主动搭台 / 你丢的东西有落点
4. **换位节律**：每周一坐 15 分钟的随员 + 遇事立刻问的军师
5. **卖 B 用 A 留 C**：军师第 1 天可验 → 随员第 1 周可验 → 分身第 30 天显形

#### Day-0 具象体验脚本（第 2 轮讨论的原始设计）
```
第一次打开（15 分钟，访谈式 onboarding）：
  首屏不是空 composer——它先问：
  ① 公司做什么、多大、客单价
  ② 眼下最头疼的一件事
  ③ 这件事你手上有几个关键数
  结束时交付：公司卡草稿 + 第一份处理单 + 回访约定

Day 1-N（有事问）：
  丢一个问题 → 处理单落在桌面「在跟的」
  会话有形状：围绕一件具体事的拍板/追问

每周一坐 15 分钟（批量通道）：
  桌面三列一屏批完
  到期行动由它先开口（晨报=到期驱动，原料全部已在家里）
```

### 走偏了什么（第二次诚实复盘）

Goal 1+2 做完之后，用户体验**没有根本变化**——产品还是聊天壳，桌面还是旁边一个 tab，auto-send 是 hack。原因是我在 plugin boundary 内的 conversation.view / input.dock 缝里加内容，这些都是「聊天壳里的附加物」，不是「独立的非聊天页面」。

### 真正的解法：sidebar.panellist + main 主区面板

vendor 有一个被忽略的机制：**sidebar.panellist + main 槽系统**。
- 生态先例：ui-schedule 用这个机制做了「自动化任务」管理页面（侧栏图标 → 点击 → 主区变成完整页面）
- 这是 **list 槽**（不是 chain 槽的 owner-only 限制）——我们已经成功注册过很多 list 槽
- **root scope**——不依赖任何 session，不需要用户先发消息，冷启动即可见

注册这个面板意味着：
- 侧栏有一个「桌面」图标（跟设置/自动化任务并列）
- 点击后**整个主区变成桌面 dashboard**——不是聊天壳里的 tab，是独立页面
- 对话变成「输入通道」：dashboard 里有入口可以进入对话
- 用户看状态/拍板/看跟进/审批——都在 dashboard 上，不需要在聊天流里翻

### 原设计与实施情况

#### Goal 1（Steps 1+2）：打开=桌面——form 层
**门禁链**：client spec / build / preflight / web-expected 两场景
**自测方法**：无头浏览器 DOM 逐帧
**完成判据**：干净 home 打开→第一眼是桌面（不是空聊天）→ 说完话→主区仍是桌面

> **历史判据。** 这句是当时的目标。当前验收见上方 R1–R7/A1–A9：无数据从一件事开始，有数据看可操作全貌；三行版式待比较；处理事项时保留对话，成功读回后才自动返回。旧 Step 2 未交付的事实保留，但不再把全局入口一概归于 D7。

#### Step 1：打开即见——空白相位自动发晨报 ⚠️ **已被取代（2026-10-08 标注，勿照此实施）**
**做什么**：用户打开产品、会话为空白时，助手**自动发第一条消息**（晨报/intake 开场），用户不需要先打字。这是「它先开口」的字面实现——产品主动说话，不是等用户先说。
**怎么做**：client bundle 检测空白会话 → 自动调 sendPrompt 发送晨报触发语 → 模型回晨报/intake 开场 → 用户看到的是一段有内容的消息，不是空屏。
**为什么可行**：loop-probe 已经在用 sendPrompt 做程序化发送——client 侧可以用同样的机制在会话空白时自动发。
**自测**：干净 home → 打开 → 不打字 → 第一条消息是助手的（晨报或 intake 开场）。

> **取代记录（2026-10-07 实施期，261007 输掉的方案 #1）**：auto-send 已退役，不要照本节实施。

**怎么做**：manual 加一条指令：「回答时检查记忆房间是否有相关上下文，有则主动引用」。
**自测**：第一轮给信息 → 第二轮问相关问题 → 回答引用了第一轮的信息。
