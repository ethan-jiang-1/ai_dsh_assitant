# 推敲：一把手的总助——用户体验重设计

> 立卡：2026-10-06 ｜ 状态：推敲中 ｜ 可关闭：否

**问题与期望结果：** 打开产品能看到业务内容，围绕桌面拍板、跟进和继续对话；用户不用从空聊天框重新交代背景。

**当前情况：** 面板入口、确定性开屏播报、上下文晨报与知识回显已有实现记录。自动发「你好」方案已退役。形态层记录见 [desk-primary-view](../../notes/implemented/2026-10-06-desk-primary-view.md)，后续行为与验收记录见 [开屏与节律卡](261007-opening-brief-and-rhythm.md)；[已归档记录](../../notes/archived/2026-10-07-opening-brief-and-rhythm.md)只作历史引用。

**未决问题：** 默认桌面（Step 2）未交付；对话处理单自动回流桌面（Goal 3 的另一方向）未单独举证。开屏卡还有技术证据缺口和用户体验判断未完成，不能说所有目标已经达成。

**下一步：** 先明确默认桌面这个已知缺口怎样处理、补齐共同验收所需证据，再准备用户体验对照。两卡共用的验收结果记在开屏卡。本次文档整理不修产品、不替用户判通过。

下面保留原设计与实施讨论；当前状态以上述摘要及各节明确标记为准。

## 走偏了什么（诚实复盘）

定位卡 18 轮讨论出了一个完整的体验重设计——**standing briefing desk**（打开=桌面，有内容等着你）。但实际执行偏成了**reactive chat + patches**（在聊天壳里加视图/技能/面板）。

| 历史设计 | 实际落地 | 差距 |
|---|---|---|
| 首开即晨报（打开=简报等着你） | 打开=空聊天框+首开条 | 晨报技能存在但需要用户先发消息 |
| 桌面=主对象（会话=动作） | 桌面=一个 tab（不是默认） | 视图 tab 不等于形态迁移 |
| 任务从三处来（它先开口/搭台/有落点） | 只有「你丢的有落点」部分工作 | 它先开口=用户先说话助手才转问 |
| 每周一坐 15 分钟 | 没有节律机制 | 无主动推送/无习惯回路 |

偏差根源：**我在做「技术能力落地」而不是「体验设计落地」**——能力是能不能做，体验是用户感受到什么。这两个是不同的事。

## 历史讨论的核心设计（要召回的东西）

### 从外部 UX 模式研究（Clay/Motion/NotebookLM/Dex）
**核心模式：聊天是对主对象的查询与操作层，不是产品的主界面。**
- Clay：首屏内容来自自动整合的既有数据，不来自用户输入
- Motion/Reclaim：主对象=日历/任务 dashboard，聊天排在主对象之后
- NotebookLM：Featured/sample 内容是零数据首跑的正规解

### 从定位卡 18 轮的定调
1. **首屏价值倒转**：首开即晨报（不是空白聊天）——产品形态从 reactive chat 变 standing briefing desk
2. **桌面为主对象**：会话降为桌面上的一种动作（像 issue 上的评论）
3. **任务从三处来**：它先开口 / 它主动搭台 / 你丢的东西有落点
4. **换位节律**：每周一坐 15 分钟的随员 + 遇事立刻问的军师
5. **卖 B 用 A 留 C**：军师第 1 天可验 → 随员第 1 周可验 → 分身第 30 天显形

### Day-0 具象体验脚本（第 2 轮讨论的原始设计）
```
第一次打开（15 分钟，访谈式 onboarding）：
  首屏不是空 composer——它先问：
  ① 公司做什么、多大、客单价
  ② 眼下最头疼的一件事
  ③ 这件事你手上有几个关键数
  结束时交付：公司卡草稿 + 第一份处理单 + 回访约定

Day 1-N（有事问）：
  丢一个问题 → 处理单落在桌面「在跟的」
  会话有形状：围绕一件具体事的拍板/追问

每周一坐 15 分钟（批量通道）：
  桌面三列一屏批完
  到期行动由它先开口（晨报=到期驱动，原料全部已在家里）
```

## 走偏了什么（第二次诚实复盘）

Goal 1+2 做完之后，用户体验**没有根本变化**——产品还是聊天壳，桌面还是旁边一个 tab，auto-send 是 hack。原因是我在 plugin boundary 内的 conversation.view / input.dock 缝里加内容，这些都是「聊天壳里的附加物」，不是「独立的非聊天页面」。

## 真正的解法：sidebar.panellist + main 主区面板

vendor 有一个被忽略的机制：**sidebar.panellist + main 槽系统**。
- 生态先例：ui-schedule 用这个机制做了「自动化任务」管理页面（侧栏图标 → 点击 → 主区变成完整页面）
- 这是 **list 槽**（不是 chain 槽的 owner-only 限制）——我们已经成功注册过很多 list 槽
- **root scope**——不依赖任何 session，不需要用户先发消息，冷启动即可见

注册这个面板意味着：
- 侧栏有一个「桌面」图标（跟设置/自动化任务并列）
- 点击后**整个主区变成桌面 dashboard**——不是聊天壳里的 tab，是独立页面
- 对话变成「输入通道」：dashboard 里有入口可以进入对话
- 用户看状态/拍板/看跟进/审批——都在 dashboard 上，不需要在聊天流里翻

## 原设计与实施情况

### Goal 1（Steps 1+2）：打开=桌面——form 层
**门禁链**：client spec / build / preflight / web-expected 两场景
**自测方法**：无头浏览器 DOM 逐帧
**完成判据**：干净 home 打开→第一眼是桌面（不是空聊天）→ 说完话→主区仍是桌面

### Step 1：打开即见——空白相位自动发晨报 ⚠️ **已被取代（2026-10-08 标注，勿照此实施）**
**做什么**：用户打开产品、会话为空白时，助手**自动发第一条消息**（晨报/intake 开场），用户不需要先打字。这是「它先开口」的字面实现——产品主动说话，不是等用户先说。
**怎么做**：client bundle 检测空白会话 → 自动调 sendPrompt 发送晨报触发语 → 模型回晨报/intake 开场 → 用户看到的是一段有内容的消息，不是空屏。
**为什么可行**：loop-probe 已经在用 sendPrompt 做程序化发送——client 侧可以用同样的机制在会话空白时自动发。
**自测**：干净 home → 打开 → 不打字 → 第一条消息是助手的（晨报或 intake 开场）。

> **取代记录（2026-10-07 实施期，261007 输掉的方案 #1）**：auto-send 已退役，不要照本节实施。
> 实测病征：判 fresh 读 `deskSlice(sid)`（新会话恒无数据 → 恒判 fresh）→ 每次重载重发，10 分钟造 6 个
> 会话、每条 ~44.6K tok；且内容物（客套+反问）本身不是设计要的「它先开口」。落地形态 = has-desk 空白
> 相位由客户端拿 walk view 确定性合成三行播报卡（零 token、天然幂等，`7fe774a`）。**本节只作历史与死路记录保留。**

### Step 2：桌面视图=默认视图 ⚠️ **未交付（2026-10-08 核对）**
**做什么**：说完第一句话后，自动切到桌面视图（view preference 已实现但时序不对——需要移到会话创建时就写入，而非渲染时）。
**怎么做**：FirstMileDock 的 inject 回调在会话绑定时就把 view preference 写入 localStorage（在 activateView 读之前）。
**自测**：说完第一句话 → 主区显示桌面（不是对话流）。

> **实况（2026-10-08 核对）**：**未交付**——261007 断点 5「view preference 写入不生效（当轮主区仍落对话）」
> 仍是 D7 未解；该卡明确把它列为非本卡范围（等上游 #8961）。本节是**未走完的路**，不是"已做的历史"。
> 「打开=桌面」当前由面板入口 + 播报卡承载（Goal 1 的意图），**不是**由默认视图切换承载。

### Goal 2（已完成）：体验深度——substance 层
结果：morning-brief 上下文简报 + 知识回显（真模型验证通过）

### Goal 3（Goal 1.5 落地后）：dashboard 与对话的双向流通 ⚠️ **半交付（2026-10-08 核对）**
**做什么**：dashboard 里的决策卡点击 → 进入拍板对话；对话里的处理单 → 自动出现在 dashboard
**自测**：dashboard → 点决策卡 → 切到对话 → 拍板 → 切回 dashboard → 决策状态更新

> **实况（2026-10-08 核对）**：**两个方向不是同一个状态**——
> 「dashboard → 对话」已交付（261007 Slice 1c：`ctx.layout.selectPanel(null)` 接通，死按钮变真入口）；
> 「对话 → dashboard 自动回流」**未单独举证**（面板刷新车道 `desk-refresh` 是现成机制，
> 但没有一行验收证据证明"对话里的处理单自动出现在 dashboard"）。本 Goal 未列入两份 implemented note 的交付清单。

### Step 3：晨报简报体验
**做什么**：到期投递（schedule follow-up 到达）时，morning-brief 的简报不是一条「你有一件事到期」——而是一段**有用的摘要**：这件事的上下文、你上次拍了什么、还缺什么数、建议下一步。
**怎么做**：morning-brief 技能扩展——到期时读桌面全部数据（不只当前 action），结合记忆房的上下文，输出一份有个性的简报。
**自测**：排一个短 due → 等投递 → 验证简报内容有上下文。

### Step 4：知识回显——「它记得我」
**做什么**：persona/技能加规则——回答中**主动引用已有记忆**（「你上次说过…」「根据你之前提到的…」），让用户感受到产品在学习。
**怎么做**：manual 加一条指令：「回答时检查记忆房间是否有相关上下文，有则主动引用」。
**自测**：第一轮给信息 → 第二轮问相关问题 → 回答引用了第一轮的信息。

> **已交付（2026-10-08 补指针）**：落在 home 手册 [home-map.ts](../../packages/dsh-smart-assistant/src/domain/home/home-map.ts)
> §"Recall what you know — every answer"（`27f8c79`）——"Before answering any question, check the memory
> room… weave it into your answer with a natural reference… The principal should never have to repeat
> something they already told you."。本卡不再复述其正文。

## 验收标准

这张旧卡已经承载实施和验收，保留原要求；本次只是澄清场景，不重定义产品完成。

| 要求 | 场景与怎么算通过 | 当前限制 |
|---|---|---|
| 第一眼是内容不是空框 | **无业务数据的新环境**显示首次使用引导；**已有业务数据、打开空白会话**显示三行业务播报（要你拍的/到期在跟/挡路的缺数）。两种场景都不需先输入「你好」 | 与开屏卡标准 #1 一致。隔离环境不等于无数据，记录时必须写清种子数据 |
| 说完话主区仍在桌面 | 发过一轮后主区不跳回聊天流，状态、跟进和拍板都在桌面上看得见 | Step 2 未交付。该项仍是缺口，等待上游或经明确决定调整范围，不能交给用户把已知技术缺口判绿 |
| 拍板读起来是本人的话 | 中文本人口吻（「拍：〈问题〉→〈选项〉」），语气由本人判断 | 技术形态与语气判断分开记录 |
| 它记得我 | 在已有业务数据的同一环境重载或隔日打开，不重发「你好」、会话不增殖 | 需可复核的重载证据；长期体验由本人判断 |
| 总体体验 | 与 2026-10-06/07 版本对照，用户判断是否达到桌面主对象的体验目标 | 旧版对照若不可重现，先说明限制；不得只问抽象的“好不好” |
