# 推敲：经营事项跨时接续是否值得成为助手主价值

> 立卡：2026-10-12 ｜ 状态：推敲中 ｜ 类型：Task ｜ 可关闭：否

**问题与期望结果：** 定位推敲提出“经营事项连续性层”假设：同一经营事项跨会话、跨几天继续时，助手带回决定依据、承诺、证据和下一步，可能减少用户重新拼现场的摩擦。现有研究较支持组织层的优先级对齐、跨部门协调和决策落地问题，但没有直接证明单个 SME 管理者需要个人决策连续性工具，也没有证明 AI 助手能解决。触发条件：用户不知道该假设是否值得做，要求至少立一张 issue 说明怎么判断。期望结果：用真实使用证据裁决该假设应继续验证、改写、延后或不做，而不是先实现新能力。完成条件：按下方验收取得真实事项证据和本人判断；结论、下游处理去向与仍未证实之处记录在卡上；达到关闭条件后归档。

**当前情况：** 本仓已有经营账本、持久回执、来源、待认领、提案与只读桌面，技术上可保存与读回事项状态；现合同见 [`docs/operating.md`](../../docs/operating.md)。研究证据与外推边界见[经营决策连续性研究](../research/positioning/261012-decision-continuity-evidence.md)：组织层问题证据中等偏强，个人管理者连续性痛点弱至中等，产品效果和采用意愿无直接证据。账本技术闭环已由旧卡验过，但这不算自然使用证据。

**未决问题：**
- 用户在真实事项跨会话时，是否实际会重讲背景、找旧材料、漏跟进，且认为这值得解决？
- 助手带回上下文后，是否减少上述摩擦，还是增加确认、维护、误关联和提醒成本？
- 有价值的连续性是事项状态与下一步、本人决策理由、跨人依赖，还是其他对象？不要预先把它们捆成“数字分身”。
- 正确的呈现时点是什么？定时晨报未获验证；机制近邻研究提示泛化辅助未必有效，提醒应贴合具体事项与触发时点。
- 判断结果适用于当前本人/试用场景，还是可以谨慎外推到目标用户？单用户证据不得冒充市场验证。

## 接续使用方案（已确认 · 2026-10-12）

> 由既有答复组装，Q9–Q14 与 2026-10-13 agent 委托进一步细化；以下描述期望行为，不代表现有读回、触发与恢复均已实现。本人是产品发起者，不作为 CEO 样本；未跑目标角色真实观察前整体仍是**候选形式**，不是已验证价值。

**一、触发场景。** 一条参与者负责、跨日继续且确有他人回复或核对点的真实经营事项，隔至少一个独立会话或一个日期后参与者回到它。不制造业务、不排练；参与者的实际角色单列，非目标角色只能证明其本人体验。原型虚构场景不计作真实触发。

**二、续接与交出（两条入口，均为现有链路）。**

- **主入口（桌面处理路径）**：桌面全景 → 在办事项「处理」→ 绑定会话（种子消息带事项标题、承诺期限/核对点、摘要，模型先 `read` 台账）→ 续接首回合**主动**交出现场包——本人追问才拿到记为一次摩擦。
- **副入口（随口续接）**：任何会话说「继续那件事/处理它」等 → 模型 `desk` 列事项、`read` 所指事项或问哪件 → 同样交出现场包。

**三、现场包 = 六件套**（行动概览后结构化复述，依据限于实际成功读回的权威资料；现有按事项 `read` 不返回完整历史，详见设计前提修正；未知与系统不可达分开）：

1. 事项目的与本人委托原话（`entrust` 逐字引用）；
2. 已确认事实与最新进展，逐条带来源（回执/来源会话）；
3. 本人已定的决定与当时依据（预测、推断不混入决定）；
4. 四种业务时间：承诺期限、外部预测、下一核对点、完成时刻（如已在）；
5. 未决与未知：待认领片段、pending 提案、明确缺口；
6. 下一步或等待条件（每条开放事项必有；没有就明说「未知」）。

**四、本人如何接着干（权限沿用现行三分，见 [docs/operating.md](../../docs/operating.md) §二，不新增）。** 现场包后助手等指令：说进展 → `report` 自动留存；明确拍板变更 → `revise`；助手推断的重大变化 → 提案等 confirm/reject；完成 → `complete` 须逐字到达证据；处理会话回执读回后桌面自动返回并选中该事项。

**五、输入负担上限（Q12 已确认细化）。** 助手追加的强制裁决/维护要求限三类：提案裁决（confirm/reject）、模糊片段认领（claim 带依据）、完成证据（逐字）；正常委托、进展与明确变更不另加确认关卡，不维持第二套日志、不逐条过目。正常业务输入仍是用户劳动，必要消歧、阅读核对、纠错重讲与其他额外维护全部记成本，不以权限三分漏算。

**六、错误与纠正路径（区分已支持与恢复缺口）。** 回复内容错/过时 → 重读并更正回复，不自动写业务；已确认状态错 → 本人明确指示后按支持字段 `revise`，误完成 → `reopen` 撤完成时刻；尚未归属的模糊片段 → `claim` 带明确依据；pending 推断提案有误 → 明确拒绝后 `reject`。已挂错材料不能用再次 claim 撤销，已生效变更不能用 reject 撤销，不支持的恢复明确记缺口。现场包未主动交出、用户须追问 → 记摩擦；必要消歧单列，不强迫猜事项。相似不同事不合并，无逐字依据不称完成；安全红线停止该事项自动推进，保留事故，待明确恢复决定，不以净收益抵消。

**七、范围与边界。** 单事项真实观察；不加机制、不实现新功能——提醒协调（核对点/到期触发）仅为未来候选，须另行授权；观察不冒充价值验证；单用户短期样本不外推市场。

**八、可执行验收（形式层——「形式被正确执行」，与下方价值层验收互补）。**

| 检查 | 通过信号 | 失败/负例 |
|---|---|---|
| 现场包齐全准确 | 事项明确后的首回应主动交出，六类实际可得资料与权威读回一致；业务未提供明确未知；决定/事实/来源可定位 | 追问才拿到、可得遗漏、预测冒充决定为 fail；已存不可达为 blocked，不以未知占位当完整恢复通过；必要消歧单列成本 |
| 入口可用 | 主入口（桌面处理路径）观察期内至少一次有效走到现场包；副入口自然用到时一并记录，不为此制造业务 | 入口断链；模型绕开台账用聊天散文结算业务变化 |
| 误关联防线 | 相似不同事并存不合并（如自然出现）；模糊材料进待认领 | 按标题合并；无依据认领 |
| 完成纪律 | 完成必有逐字到达证据；reopen 可撤 | 「应该已经付了」类说法被当证据 |
| 负担在限内 | 追加强制维护限三类，不加逐条确认；正常业务输入、消歧、核对、纠错等成本分别记录 | 要逐条过目或重复填表才能维持；漏算纠错/阅读成本 |

价值层判断（摩擦是否真减、净收益是否为正）仍归本人，按下方 `## 验收标准` 两行执行；形式层验收通过 ≠ 价值验证通过。

**九、落地前置约束（本人要求，2026-10-12）。** 适用于任何后续动用户可见面或实施新能力的落地——含未来提醒候选（核对点/到期触发）与观察暴露缺口的修补；不改变本轮观察不加机制的边界：

- **UX 设计是重中之重**：凡动用户可见面——现场包的呈现话术与信息层级、桌面处理路径入口、开屏指向卡、未来提醒提示——UX 先设计好再动手；层级与话术经真机走查（`pnpm desk-walk`）供本人判断，渲染证据走 `pnpm shots` / web-face 场景，不以测试绿替代 UX 判断。先例教训见[唯一桌面决定](../../notes/implemented/2026-10-11-one-operating-desk.md)：用户脑海里同名面只有一张，第二张同名面就是回归。
- **落地前思考好测试资产与测试策略**：按 [validation-evidence](../methods/validation-evidence.md) 方法把上方形式层验收逐行指到 [docs/testing.md](../../docs/testing.md) 证据地图的证据 owner 与既有资产；缺的资产先立再动手（如 eval 行为任务）；模型可见面改动按包纪律走真实组合测试与 `pnpm eval`——不以单测绿冒充行为或 UX 证据。
- **充分利用 DSH 已有机制**：落地前先核对钉住版本的扩展点、实际组合与能力边界，优先复用，不另造会话、审批、任务状态或排程系统。平台有能力不等于本插件已接好业务链路；尤其不能把原生 schedule 当作经营提醒协调已完成。

**UX 先设计的是接着办事的过程，不只是六件套排版。** 后续切片先给出主入口与副入口的完整状态流、代表性话术和失败/恢复路径，再确定组件或 prompt：

- **首回合信息层级**：优先让本人看清「现在到哪了、等什么/下一步是什么、是否有需本人裁决的变化」，六件套仍须齐全；依据紧邻相应事实，长来源可按需回查，不倒出整份流水。长短事项分别检查，不靠缩字或删掉未知项制造简洁。
- **不把展示变成确认劳动**：读回现场包不要求逐项确认，不另设“确认现场包”关卡；不以重讲委托或再填一张表作为正常续接前置。需要本人出手的情况仍按方案第五节执行。
- **错误与恢复可辨认**：分别设计无事项、指代不明/相似事项、读回中、读回失败/陈旧、待裁决与纠错后的呈现。没读到最新台账就不假装恢复成功；缺来源或决定依据要明说未知，不能补造。不得把“已经回复”表现成“已提交”，也不得以恢复异常为理由扩大确认负担。
- **导航不抢工作**：沿用唯一桌面与绑定处理会话，不增第二张同名面。本人离开处理路径后，迟到回执不得把人拉回；续接只读现场包本身也不得触发业务成功返回。桌面返回仍遵守现有回执读回条件，而非对话结束条件。

### 已核实的设计前提修正

这些是源码事实，不是修改本人已确认的目标；旧方案中对应的“已具备”说法以这里的核查为准。

1. **保存了 ≠ 模型能按事项完整读回。** [事项 read](../../packages/dsh-smart-assistant/src/agent/tool-operating/index.ts#L284) 返回事项摘要结构、材料和提案摘要，不返回初始 create/entrust 原话、已确认变更的完整操作历史与可遍历 operation id；[deskItem](../../packages/dsh-smart-assistant/src/agent/tool-operating/index.ts#L84) 也不返回 summary、responsible、forecastSource、completedAt，提案摘要不返回具体 change 目标值。[按 operation id 回查](../../packages/dsh-smart-assistant/src/agent/tool-operating/index.ts#L308) 需要先知道 id；全局待认领只能由 `desk` 取得，不能因标题相似列作本事项材料。故六件套第 1/3/4/5/6 件有读回或业务资料缺口，不能宣称一次 `read` 的“台账全文”已能交出完整现场包；真实观察必须如实记缺失，不能偷偷改功能补齐。
2. **主入口会话新旧有条件。** [processMatter](../../packages/dsh-smart-assistant/src/client/index.ts#L213) 若已有同事项的内存绑定则重开该会话，不重发种子；否则新建会话并绑定。[种子指令](../../packages/dsh-smart-assistant/src/client/desk-process.ts#L447) 是先读台账再等具体指令，没有主动六件套要求。刷新后绑定路径不重放；“回来就主动交出”在复用会话、跨日回访和只读首轮的触发语义仍需确认，不能称所有续接场景现成支持。**（2026-10-13 第三切片更新：重开不重发种子的缺口已按 Q11 修复——重开分支现发续接种子，见下方第三切片记录；刷新后路径不重放仍是有意设计，刷新后点「处理」走新会话+完整种子。）**
3. **纠错不是统一撤销。** [claim](../../packages/dsh-smart-assistant/src/domain/operating/ledger.ts#L404) 从待认领中取材料并消费该片段，不提供解除既有归属/迁移已挂材料的动作；[reject](../../packages/dsh-smart-assistant/src/domain/operating/ledger.ts#L650) 仅对 pending 提案生效，不撤已确认变更。回复误述可重读更正；已写错状态只有工具实际支持的 revise/reopen 等才能纠正，不支持的必须记恢复缺口，不能承诺“claim/reject 即可恢复”。
4. **权限三分不等于只有三种自然表达。** 已确认的三分是自动进展、明确指令、推断提案。原方案第五节若按“仅三种本人动作”字面验收，会排除原方案第四节必要的明确委托、revise 指示和纠错理由。建议负担衡量针对额外重复录入、重复确认与维护劳动，正常业务指示单列；尚不擅自替换本人已确认的负担上限。
5. **现有 eval 不证明跨时六件套。** [runPreset](../../dev/eval/run.mjs#L93) 每题新建工作目录/会话，但共享所选 dev home，串行不等于隔离账本；[observe](../../dev/eval/run.mjs#L44) 当前提取工具调用与拼接回答，不能直接判首轮时序、成功读回结果或字段与来源准确性。聚焦题目还须明确台账前置、独立会话、结果判定与清理；缺检查不能用回答关键词补成通过。

**原型问题与授权范围：** 一位负责人隔几天回来，能否从唯一桌面进入一件事，先看清现状与待裁决，再自然地继续，而不用维护另一套日志？交出离线、内存模拟的可操作 HTML；原型表现拟议的完整体验，绝不当作真实 DSH 链路验收。三个结构对照共享同一组虚构事项：A 行动概览（推荐）、B 事项工作台、C 接续对话；以 A 为默认，不把再选一轮布局当阻塞。只覆盖恢复与处理流，不仿造经营全系统；原型状态、模拟回执及错误均可见。

### Agent 选定的需求细则（可逆默认 · 未经目标用户验证）

- **下一步的权限**：分“已定下一步/等待条件”与“助手建议”。从资料能明确恢复的动作原样带回；缺少下一步时说未知，可另外给一条标注建议，不能自动盖为决定、创建任务、改核对点或代表负责人联系外部。提案不把等待显示成已生效。
- **六件套的齐全**：齐全指六类均有忠实内容或明确未知，不是必须凑六条肯定事实；已保存却不可读与业务未提供分别标记。可得资料遗漏为 fail；不可达为 blocked；未知如实表达可通过诚实性检查，但仍不能证明缺失事实被恢复。委托原话保留逐字证据，目的复述与原话分开；来源按回执/会话定位，未获来源不补链接。
- **事实与时间**：已确认只描述负责人明确指示与已提交状态；客户说法属于外部材料，不等同独立查证。当前时间值与历史变更分开，承诺、预测、核对点、完成时刻不互相替代；未完成时完成时间不适用，不为填齐盖时间。下次读取以台账当前 revision 为准，不声称现实世界一定最新。
- **明确续接**：桌面“处理”无论新建或复用绑定会话都表达一次续接意图；普通打开旧聊天不播报。副入口无唯一身份则只给最少候选并问哪件，不按标题合并，不倾倒全局待认领；消歧后的首次回应开始计算首回合。同一处理中补进展仅显示相关变化/回执，不反复整包。用户先发新进展时优先承接进展，读回提交结果后呈现受影响内容，不再让用户重说。
- **状态与导航**：唯一桌面保留选择 → 绑定会话 → 读回中 → 主动现场包或失败提示 → 用户输入/待裁决 → 持久提交与同操作新鲜回执 → 返回并仍选该事项。只读、追问、提案 pending、陈旧/错会话/错事项回执不得成功返回；本人手动返回/离开不触发写入，迟到提交不抢导航。重复入口不创建重复业务操作；刷新/中断重新核对，不盲目重放操作。
- **错误恢复**：回复误述只重读更正，不为纠正文字另写业务；pending 错提案可按明确指令 reject；已生效错状态在本人明确指示后仅使用支持字段的 revise/reopen。材料挂错、已完成提案撤销、未支持字段清空等不承诺有现成恢复通道。遇安全红线保留事故、停自动推进，不将试错痕迹抹成成功；恢复须指出受影响内容与实际可恢复范围，未支持则留缺口待另行授权。
- **输入与异常**：口语进展/确认性指令沿用现有权限；不要求六项表单。复合输入可先保留普通材料，再将重大推断提案，回复分别说明已留存与待确认。模型不确定/拒绝或业务写入失败须报告未完成、已提交与否和可恢复路径；不把模型自报或盲目重试算成功。超出事项权限的执行只给建议，不代收付款、发消息或签约。
- **UX 默认**：一小段行动概览后覆盖六类，时间/来源就近，决定与预测/建议/未知有文字标签，不只靠颜色。列表/详情与会话是同一桌面的处理路径，不创第二桌面；长资料展开但不能隐藏承诺与待裁决。检查窄宽屏、键盘焦点、按钮可用态与长中文/数字，不用固定字号缩放遮掩溢出。默认不设摘要字数门槛，用是否看清现状与行动来判断。
- **隐私与数据**：原型只用虚构合同、金额与联系人；无网络、无持久存储、无真实台账读写，不假装接入微信/财务系统。后续真实取证须由参与者明确选择低风险材料；仅保留必要事件/回执/匿名化片段，报告不复制无关经营细节，不能把系统审批绕过当作体验优化。
- **观察与成本**：两周自然观察复看采用本轮设计/原型交付日 2026-10-13 至 2026-10-27；这是复看窗口，不是假定已有目标用户/真实事项、不是自动提醒。不要求用户恢复同一现场两遍；有自然基线则记实测/估计来源，无则记无对照。所有正常输入、核对阅读、必要裁决/消歧、重讲纠错计成本；观察记录与开发成本单列。到期无样本需本人决定延长/延后/暂缺证据结束，不自动关卡。

## 已知与未决

### 已知事实

- 经营账本将明确委托、普通进展、推断性提案分别处理，并保留 operation receipt、来源会话及四种业务时间；桌面投影是只读，见 [`docs/operating.md`](../../docs/operating.md)。
- 研究支持的重点是组织层优先级、跨单元协调、资源承诺与复盘存在断点；没有找到直接测试 SME 管理者个人决策历史或本地 AI 连续性助手效果的研究。
- 一项丹麦公立学校现场实验发现提醒效果在实施阶段消失；空管模拟研究发现外部辅助只有在目标出现时提供诊断性线索才有效。它们只构成提醒设计的机制警示，不直接代表企业效果。
- 旧卡 [CEO 经营闭环](../_archive/settled_issues/261008-ceo-operating-loop.md)拥有账本技术语义、事项归属和跨 Session 识别验收；本卡不重开、不复制这些技术问题，只问真实连续性价值。

### 假设（待验证）

- 真实经营事项会自然跨会话，用户会在续接时遇到可观察的恢复成本。
- 来源可追、且只在相关时点呈现的上下文可能降低恢复成本。
- 若助手需要用户频繁手工建账、确认每个轻微变化或处理泛化提醒，维护成本可能超过收益。

### 方案与取舍

暂定采用“单事项、跨时、观察行为与成本”的最小验证，不先做功能切片。比较对象是同一真实工作中当前实际发生的恢复方式，不要求用户额外维持第二套日志；观察记录由试用过程完成，不能把开发/eval/演示会话当真实效果。

考虑过但暂不采用：

- **直接把连续性定为定位并实现晨报/承诺检测**：拒绝。研究没有验证产品解法，提醒实验也提示启动与持续实施不是一回事。
- **仅用一次演示或模拟事项验收**：拒绝。能证明工具可运行，不能证明用户有此痛点或愿意付维护成本。
- **先做更完整的决策日志/知识治理**：拒绝。未证实日志提高决策质量；当前先观察已有账本是否在真实跨时事项中带来价值。

- 产品推论（含探针/技术合同）**不得**当作产品效果证据（`docs/operating.md` 是技术合同，不是价值证明）。

**两条出口（关闭条件原文的两支，选一并在卡上写明）**：

- **有观察** → 按验收标准逐栏记录，形成结论（保留为候选价值 / 缩窄到事项接续与来源回查 / 延后并写重看触发 / 不做并说明原因）；
- **未出现可观察事项** → **明确记录"未出现"** 并取得本人同意后以「暂缺证据」结束（延长须落新的明确日期）。

**不许的形态**（验收标准第三行的负例，复看时逐条自检）：把无事件写成负面或正面证明；用模拟/工具测试证明产品效果；用组织调查证明个人需求；把技术测试当价值证据。

## 验收标准

| 行为 / 需求 | 类别 | 输入与状态 | 通过信号 | 失败/负例 | 证据所有者与限制 | 人的判断 |
|---|---|---|---|---|---|---|
| 真实事项跨时续接后，是否减少现场恢复摩擦 | 模型行为 + 编排 + 用户行为 | 实际参与者角色明确，自然事项在不同日期/会话继续，不制造业务；原型不入样本 | 记录重讲/查找/追问与恢复起止；用户劳动/模型等待/外部等待分开，实测/估计区分；准确带回事实/决定/来源/未知/下一步，并指出省掉的真实步骤；无对照明说无对照 | 未触发记无证据；完整能力缺口记 blocked；冗长不省事、仍完整重讲为负价值候选；误关联/伪造等安全事故不能被收益冲抵 | 账本回执/会话来源及桌面读回；观察住本卡；技术合同 [`docs/operating.md`](../../docs/operating.md)。技术测试不证明价值，非目标角色不外推目标用户 | 参与者判断是否省下有意义工作、愿否继续；本人决定产品去向；agent 不替代真实体验结论 |
| 维护与提示成本是否低于收益 | 模型行为 + 人的行为 | 同一事项记录正常输入、投递、阅读核对、裁决/消歧、纠错重讲与打断；观察/开发成本单列 | 参与者判断收益大于维护/打断成本并指出具体省掉步骤；无提醒事件记不适用 | 维护劳动更多、归属反复澄清、没有净收益；不漏算纠错、不把未发生提醒判有效 | 日志可重取行为与次数；线下劳动/打断感受标明一次事后估计；单用户短期不外推市场 | 参与者判断可接受成本与打断，本人据边界决定产品取舍 |
| 结论是否能诚实区分证据与外推 | 分析任务 | 汇总本卡观察与[调研证据](../research/positioning/261012-decision-continuity-evidence.md) | 结论区分组织级研究、个人实测、产品推论；明确样本边界和未测内容 | 用组织调查证明个人需求；用模拟/工具测试证明产品效果；把无事件写成负面或正面证明 | 调研档、真实观察及本卡结论 | 无额外判断；证据边界由卡片审阅核对 |
