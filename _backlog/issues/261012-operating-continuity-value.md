# 推敲：经营事项跨时接续是否值得成为助手主价值

> 立卡：2026-10-12 ｜ 状态：推敲中 ｜ 类型：Task ｜ 可关闭：否

**问题与期望结果：** 定位推敲提出“经营事项连续性层”假设：同一经营事项跨会话、跨几天继续时，助手带回决定依据、承诺、证据和下一步，可能减少用户重新拼现场的摩擦。现有研究较支持组织层的优先级对齐、跨部门协调和决策落地问题，但没有直接证明单个 SME 管理者需要个人决策连续性工具，也没有证明 AI 助手能解决。触发条件：用户不知道该假设是否值得做，要求至少立一张 issue 说明怎么判断。期望结果：用真实使用证据裁决该假设应继续验证、改写、延后或不做，而不是先实现新能力。完成条件：按下方验收取得真实事项证据和本人判断；结论、下游处理去向与仍未证实之处记录在卡上；达到关闭条件后归档。

**当前情况：** 本仓已有经营账本、持久回执、来源、待认领、提案与只读桌面，技术上可保存与读回事项状态；现合同见 [`docs/operating.md`](../../docs/operating.md)。研究证据与外推边界见[经营决策连续性研究](../research/positioning/261012-decision-continuity-evidence.md)：组织层问题证据中等偏强，个人管理者连续性痛点弱至中等，产品效果和采用意愿无直接证据。账本技术闭环已由旧卡验过，但这不算自然使用证据。

**未决问题：**
- 用户在真实事项跨会话时，是否实际会重讲背景、找旧材料、漏跟进，且认为这值得解决？
- 助手带回上下文后，是否减少上述摩擦，还是增加确认、维护、误关联和提醒成本？
- 有价值的连续性是事项状态与下一步、本人决策理由、跨人依赖，还是其他对象？不要预先把它们捆成“数字分身”。
- 正确的呈现时点是什么？定时晨报未获验证；机制近邻研究提示泛化辅助未必有效，提醒应贴合具体事项与触发时点。
- 判断结果适用于当前本人/试用场景，还是可以谨慎外推到目标用户？单用户证据不得冒充市场验证。

**下一步：** 先做一轮真实事项观察，不改产品、不加提醒机制；执行形态按下方已确认的《接续使用方案》（六件套现场包、回访时主动交出、桌面处理路径主入口、随口续接副入口、权限三分负担上限、落地前置约束）。首个观察事项暂无预定（2026-10-12 拍板：等自然出现），自然发生时由本人选一条未来数日确有外部依赖或核对点的经营事项，在现有助手中自然处理；事项跨至少两个独立会话或两个日期后，观察回到该事项时是否能带回来源、已确认决定、当前状态、未知项与下一步。分别记录用户实际重讲/翻找/追问/纠错/忽略提醒的行为与耗时；观察结束后由本人判断净收益是否超过投喂与确认成本。若观察期内没有自然事项、没有跨时继续，记录为“无证据/未触发”，不得用模拟数据判成功。研究材料：[经营决策连续性研究](../research/positioning/261012-decision-continuity-evidence.md)。不实施新功能，除非本卡结论另行授权。

## 本轮需求澄清

**触发条件：** 本人点名本卡，要求理解诉求背后的意图，按 methods 的要求充分敲打，并具象化为今后可以落地的形式。

**本人应得到什么：** 一份经过本人确认的具体使用方案，说明何种真实场景触发、助手交出什么、用户如何继续工作；明确输入负担、权限、错误与纠正路径、范围和验收标准。未确认的候选形式保持为假设。

**本轮完成条件：** 按决策依赖分轮确认业务选择，将回答、实际比较的方案与理由、失败/恢复情形和可执行验收写回本卡，使后续会话能据此继续。未来实施仍以实际授权为准；本轮设计完成不等于上文连续性价值已通过真实使用验证，不替代原有关闭条件。

**第一轮已确认（本人答复）：**

- Q1 本人选择 A「恢复现场、接着办」，作为优先主价值。承诺推进与判断依据是否以及如何支撑，后续按该主价值界定，不同时扩张为三个主价值。
- Q2 本人答「我听你的建议」：采用一条本人负责、几天后继续且涉及他人回复或核对的真实事项作为首个验证对象。这确认了选取原则，未提供具体事项、已发生断点或业务材料；场景示例不是本人经历，痛点发生与净收益仍待观察。

**第二轮已确认（本人答复，2026-10-12）：**

- Q3 现场包内容：选「六件套结构化现场包」。比较过并拒绝：维持现状薄现场（种子卡只带标题+承诺/核对+摘要，决定/来源/未知项不保证带回，观察退化为查状态）；全量读回（全文+回执流水一次倒出，噪声成本高，研究提示不贴合时点的泛化倾倒无优势）。
- Q4 出现时点：选「本人回访时」——主入口 = 桌面「处理」绑定会话，副入口 = 随口续接，均现有链路、零新机制，贴合「线索只在相关事项出现时给」的机制约束。核对点/到期触发记为**未来候选**（提醒协调现为恒空占位，需另行授权，不进本轮）；开屏主动播报**拒绝**（现无此链路、研究提示泛化播报无优势且违反本轮不加机制）；只读桌面面板记为**已有补充**。
- Q5 输入负担：选「现行权限三分即上限」。更轻（不点名自动立账）违反「归属永不按标题猜」的已确认决定、推高误关联；更重（逐条过目）确认次数本身即成本，大概率净负。
- Q6 首个观察事项：暂无，等自然出现——方案先定；观察期内无自然跨时事项则记「无证据/未触发」，不得用模拟数据判成功。

**终轮已确认（本人答复，2026-10-12）：** 《接续使用方案》整体成立；现场包为续接首回合**主动**交出——本人追问才拿到记为一次摩擦（此观察项自本确认起生效）。本轮设计收口：诉求已具象化为可落地、可观察、可判输赢的使用方案，后续会话按该方案与卡首「下一步」节的观察协议执行即可，不需再猜。价值观察仍未开始——等自然事项触发；本轮设计完成不等于连续性价值已验证，不替代原关闭条件。

**事实核查：** 现合同支持事项、进展、来源与回执保存/读回；确认性变化须本人明确指示，推断性重大变化须提案，见 [`docs/operating.md`](../../docs/operating.md)。该合同明确 v2 reminders 恒空占位，已有排程能力不能视为账本原生提醒协调完成。既有续接链路本轮已核对（源码与[唯一桌面决定](../../notes/implemented/2026-10-11-one-operating-desk.md)）：桌面**处理路径**已在——在办事项绑定处理会话，种子消息带入标题、承诺期限/核对点与摘要并指示模型先 `read` 台账再等指令，绑定后回执读回时桌面自动返回并选中该事项（[desk-process.ts](../../packages/dsh-smart-assistant/src/client/desk-process.ts)，面板层已接线）；**随口续接**已在——本人说「处理它/继续」未点名时模型 `desk` 列事项、`read` 所指事项或问哪件，禁止翻文件系统/会话日志重建意图（[operating-brief](../../packages/dsh-smart-assistant/src/agent/operating-brief/index.ts)）；**开屏不播报经营事项**——旧会话桌面播报随会话桌面退役（2026-10-11），现开屏卡零 token、只指向桌面全景。不以技术可保存/读回代替业务价值证明。

## 接续使用方案（已确认 · 2026-10-12）

> 由 Q1–Q8 已确认答复组装；未跑真实观察前整体仍是**候选形式**，不是已验证价值。

**一、触发场景。** 一条进行中的真实经营事项（本人负责、跨日继续、确有他人回复或核对点），隔至少一个独立会话或一个日期后本人回到它。不制造业务、不排练。

**二、续接与交出（两条入口，均为现有链路）。**

- **主入口（桌面处理路径）**：桌面全景 → 在办事项「处理」→ 绑定会话（种子消息带事项标题、承诺期限/核对点、摘要，模型先 `read` 台账）→ 续接首回合**主动**交出现场包——本人追问才拿到记为一次摩擦。
- **副入口（随口续接）**：任何会话说「继续那件事/处理它」等 → 模型 `desk` 列事项、`read` 所指事项或问哪件 → 同样交出现场包。

**三、现场包 = 六件套**（一段结构化复述，来源 = `read` 返回的台账全文）：

1. 事项目的与本人委托原话（`entrust` 逐字引用）；
2. 已确认事实与最新进展，逐条带来源（回执/来源会话）；
3. 本人已定的决定与当时依据（预测、推断不混入决定）；
4. 四种业务时间：承诺期限、外部预测、下一核对点、完成时刻（如已在）；
5. 未决与未知：待认领片段、pending 提案、明确缺口；
6. 下一步或等待条件（每条开放事项必有；没有就明说「未知」）。

**四、本人如何接着干（权限沿用现行三分，见 [docs/operating.md](../../docs/operating.md) §二，不新增）。** 现场包后助手等指令：说进展 → `report` 自动留存；明确拍板变更 → `revise`；助手推断的重大变化 → 提案等 confirm/reject；完成 → `complete` 须逐字到达证据；处理会话回执读回后桌面自动返回并选中该事项。

**五、输入负担上限。** 仅三类事需本人出手：提案裁决（confirm/reject）、模糊片段认领（claim 带依据）、完成证据（逐字）。其余自动留存；不维持第二套日志、不逐条过目。

**六、错误与纠正路径（全部为现有通道）。** 现场包内容错/过时 → 本人指出，助手重读 `read` 并走对应通道：已确认状态错 → `revise`；误完成 → `reopen`（撤完成时刻）；归属错 → 待认领/`claim` 带明确依据；推断被写成决定 → `reject` 提案。现场包未主动交出、本人须追问 → 记一次摩擦（已确认的观察项）。相似不同事不得合并（归属永不按标题猜）；无逐字依据不得称完成。

**七、范围与边界。** 单事项真实观察；不加机制、不实现新功能——提醒协调（核对点/到期触发）仅为未来候选，须另行授权；观察不冒充价值验证；单用户短期样本不外推市场。

**八、可执行验收（形式层——「形式被正确执行」，与下方价值层验收互补）。**

| 检查 | 通过信号 | 失败/负例 |
|---|---|---|
| 现场包齐全准确 | 续接首回合**主动**交出，六件套均在且与 `read` 台账一致；决定/事实/来源可指向回执 | 须本人追问才拿到（记摩擦）；缺件；把预测或推断写成决定；内容过时未重读 |
| 入口可用 | 主入口（桌面处理路径）观察期内至少一次有效走到现场包；副入口自然用到时一并记录，不为此制造业务 | 入口断链；模型绕开台账用聊天散文结算业务变化 |
| 误关联防线 | 相似不同事并存不合并（如自然出现）；模糊材料进待认领 | 按标题合并；无依据认领 |
| 完成纪律 | 完成必有逐字到达证据；reopen 可撤 | 「应该已经付了」类说法被当证据 |
| 负担在限内 | 出手事项仅限三类且次数记录在案 | 需要逐条过目才能维持账本 |

价值层判断（摩擦是否真减、净收益是否为正）仍归本人，按下方 `## 验收标准` 两行执行；形式层验收通过 ≠ 价值验证通过。

**九、落地前置约束（本人要求，2026-10-12）。** 适用于任何后续动用户可见面或实施新能力的落地——含未来提醒候选（核对点/到期触发）与观察暴露缺口的修补；不改变本轮观察不加机制的边界：

- **UX 设计是重中之重**：凡动用户可见面——现场包的呈现话术与信息层级、桌面处理路径入口、开屏指向卡、未来提醒提示——UX 先设计好再动手；层级与话术经真机走查（`pnpm desk-walk`）供本人判断，渲染证据走 `pnpm shots` / web-face 场景，不以测试绿替代 UX 判断。先例教训见[唯一桌面决定](../../notes/implemented/2026-10-11-one-operating-desk.md)：用户脑海里同名面只有一张，第二张同名面就是回归。
- **落地前思考好测试资产与测试策略**：按 [validation-evidence](../methods/validation-evidence.md) 方法把上方形式层验收逐行指到 [docs/testing.md](../../docs/testing.md) 证据地图的证据 owner 与既有资产；缺的资产先立再动手（如 eval 行为任务）；模型可见面改动按包纪律走真实组合测试与 `pnpm eval`——不以单测绿冒充行为或 UX 证据。
- **充分利用 DSH 已有机制**：落地前先核对钉住版本的扩展点、实际组合与能力边界，优先复用，不另造会话、审批、任务状态或排程系统。平台有能力不等于本插件已接好业务链路；尤其不能把原生 schedule 当作经营提醒协调已完成。

### 落地推敲补充（本轮要求与技术建议）

**触发 / 交出 / 完成：** 本人再次强调 UX 为重中之重、测试资产与策略须前置、充分利用 DSH 机制；本轮交出这三项的具体落地检查与已知证据缺口，写回本卡供后续设计使用。完成以约束、证据路线和未验证边界明确为准；不改产品、不新建测试框架、不开始价值观察。以上三项为本人明确要求；下方是 agent 对要求的细化建议，不冒充已经过本人体验确认的最终 UX。

**UX 先设计的是接着办事的过程，不只是六件套排版。** 后续切片先给出主入口与副入口的完整状态流、代表性话术和失败/恢复路径，再确定组件或 prompt：

- **首回合信息层级**：优先让本人看清「现在到哪了、等什么/下一步是什么、是否有需本人裁决的变化」，六件套仍须齐全；依据紧邻相应事实，长来源可按需回查，不倒出整份流水。长短事项分别检查，不靠缩字或删掉未知项制造简洁。
- **不把展示变成确认劳动**：读回现场包不要求逐项确认，不另设“确认现场包”关卡；不以重讲委托或再填一张表作为正常续接前置。需要本人出手的情况仍按方案第五节执行。
- **错误与恢复可辨认**：分别设计无事项、指代不明/相似事项、读回中、读回失败/陈旧、待裁决与纠错后的呈现。没读到最新台账就不假装恢复成功；缺来源或决定依据要明说未知，不能补造。不得把“已经回复”表现成“已提交”，也不得以恢复异常为理由扩大确认负担。
- **导航不抢工作**：沿用唯一桌面与绑定处理会话，不增第二张同名面。本人离开处理路径后，迟到回执不得把人拉回；续接只读现场包本身也不得触发业务成功返回。桌面返回仍遵守现有回执读回条件，而非对话结束条件。

**DSH 复用要具体到职责，而不是“都用上”。** 机制依据走 [平台架构](../../vendor/dsh/docs/architecture.md) → [能力图](../../vendor/dsh/docs/capability-seams.md) → 对应 owner；不在本卡复制平台 API：

- **用户工作流**：桌面只负责选事项、进入绑定会话与读回；对话继续沿用原生会话、工具调用及交互机制，业务权限仍由账本三分守住。技术操作审批不替代业务提案裁决，也不重复加一层审批。
- **呈现与可追溯**：有 UI 改动时沿用 [Slot 生命周期](../../vendor/dsh/docs/subsystems/slots.md) 与本包主题/本地化约束；工具展示复用既有 presenter 通道。模型上下文与工具结果须能从原生会话日志重建，业务事实仍以账本与持久回执为准；不靠扫描旧聊天猜事项归属，也不建立第二份可写真相。
- **研发过程**：复杂实施用原生 plan 呈批、todo 活清单和可随时 steer 的机制；仅在确为长期目标时使用 goal，不把本卡自动转为持续实施任务。未来提醒获授权后再审原生 schedule 的组合可达性、重复调度/撤销/恢复及提醒成本，不能借机制复用越过本轮“不加提醒”的边界。

**后续落地的停止条件：** UX 状态流未设计、某项验收没有可重跑证据路线，或所依赖的 DSH 能力仅凭猜测时，先补设计/证据/机制核查，不以“先接起来”进入实现。最终话术、层级与真实使用价值仍待实际走查和自然事项观察；本补充不改变卡的状态与关闭条件。

## 已知与未决

### 已知事实

- 经营账本将明确委托、普通进展、推断性提案分别处理，并保留 operation receipt、来源会话及四种业务时间；桌面投影是只读，见 [`docs/operating.md`](../../docs/operating.md)。
- 研究支持的重点是组织层优先级、跨单元协调、资源承诺与复盘存在断点；没有找到直接测试 SME 管理者个人决策历史或本地 AI 连续性助手效果的研究。
- 一项丹麦公立学校现场实验发现提醒效果在实施阶段消失；空管模拟研究发现外部辅助只有在目标出现时提供诊断性线索才有效。它们只构成提醒设计的机制警示，不直接代表企业效果。
- 旧卡 [CEO 经营闭环](../_archive/settled_issues/261008-ceo-operating-loop.md)拥有账本技术语义、事项归属和跨 Session 识别验收；本卡不重开、不复制这些技术问题，只问真实连续性价值。

### 假设（待验证）

- 真实经营事项会自然跨会话，用户会在续接时遇到可观察的恢复成本。
- 来源可追、且只在相关时点呈现的上下文可能降低恢复成本。
- 若助手需要用户频繁手工建账、确认每个轻微变化或处理泛化提醒，维护成本可能超过收益。

### 方案与取舍

暂定采用“单事项、跨时、观察行为与成本”的最小验证，不先做功能切片。比较对象是同一真实工作中当前实际发生的恢复方式，不要求用户额外维持第二套日志；观察记录由试用过程完成，不能把开发/eval/演示会话当真实效果。

考虑过但暂不采用：

- **直接把连续性定为定位并实现晨报/承诺检测**：拒绝。研究没有验证产品解法，提醒实验也提示启动与持续实施不是一回事。
- **仅用一次演示或模拟事项验收**：拒绝。能证明工具可运行，不能证明用户有此痛点或愿意付维护成本。
- **先做更完整的决策日志/知识治理**：拒绝。未证实日志提高决策质量；当前先观察已有账本是否在真实跨时事项中带来价值。

## 关闭条件

- 有一条真实事项跨至少两个独立会话或日期的有效观察，按 `## 验收标准` 记录实际恢复行为、助手读回内容、错误/纠正、用户投入成本和本人判断；或明确记录在合理观察期内未出现可观察事项，并得到本人同意以“暂缺证据”结束本轮。
- 卡上形成明确结论：保留为候选价值、缩窄到事项接续/来源回查、延后并写清重看触发，或不做并说明原因；区分事实与推断。
- 需要下游处理的申请已提交并记录去向；若结论只回答问题，留下依据链接即可。满足后才写“可关闭：是”并归档。
