# 推敲：CEO 的持续助理——跟踪事情、适时提醒与建议、从结果中学习

> 立卡：2026-10-08 ｜ 关闭：2026-10-09 ｜ 状态：已结 ｜ 类型：未定 ｜ 结论：做有界设计/验证 ｜ 去向：2026-10-09 本轮回复向当前用户提出下游处理申请（见末节），尚未创建 note 或授权实现

**问题与期望结果：** 用户再次反馈，项目开发已久仍“不痛不痒”，难以打动 CEO。用户明确强调提醒与主动建议、事物跟踪、经验沉淀和学习，并要求把调整思路组织到 issues、支持证据放 research。希望助手持续接住经营事项，在繁重日常中减少本人重新整理背景、判断该管什么和反复追进展的负担，并把结果与纠正用于下一次工作。

**外部结果三要素：** 触发＝本人交代一件需持续关注的事，或已有事项出现进展、新材料、到期、约束变化、纠正；用户得到＝可接续的事情记录，以及有依据、说明“为何现在需要你”的提醒或建议，反馈后记录和后续跟进同步，下一件类似工作能正确使用已经确认的经验；完成条件＝先形成能复述这一过程的需求与范围，通过有界情景比较得到机制/交互证据，确定可执行验收和后续处理申请。模拟可验证过程，不能据此宣布真人经营价值或长期学习已成立。

**当前情况：** 历史定位和调研已有这些诉求，现有载体包括决定、行动、缺口、记忆、知识、技能与排程；已有证据主要覆盖单轮分析、记录、局部交互和排程写入。跟踪、注意力筛选、主动判断与条件化学习尚未形成共同验证过的过程。

**下游待验问题：** 最少输入、介入理由、完成依据和条件经验已有可检验方案；相对现有版/普通聊天的增量、真实恢复与模型守约仍待后续证据。关注阈值、语气与真实净收益按 V6/V9 由本人判断，不由本轮模拟或常规测试代答。

**本轮结论：** 用户确认先用回款承诺，并采用普通材料自动留存、明确指令直接执行、模型推断的重大变化先确认的权限方案；有界方案、恢复协议与验收已形成。2026-10-09 已在本轮回复向当前用户提出下游设计/验证申请，去向与内容见末节。本卡按 backlog 条件关闭；源码复核和模拟不等于现有版实测、模型守约或本人采纳，不授权产品实现。

**下一步的接手范围：** 下游按 notes 规则处理申请，先承担 V1–V5/V7，再明确承接 V6/V8/V9。现状复验、模型比较与持久恢复证据由后续切片依验收取得，不要求尚未实施的检查先通过；不扩大输入通道或将未验证价值写成已成立。

### 统一经营账本与多会话输入（已确认）

**用户确认：** 一个权威经营账本可接收多个 Session 的输入，保留来源 Session 与原始记录追溯。桌面给完整事项列表、有依据的优先建议和下一步，CEO 保持自选权；证据不足时承认不能判断，不编造确定排序。一个账本不等于只许一个聊天会话，也不等于把不同工作区的所有文件自动混在一起。

**本卡拥有：** 事项身份与接续、何为最新已确认进展、提醒/建议依据、经验条件，以及多个会话输入如何成为经营账本的可信更新。[总助体验卡](../../issues/261006-chief-of-staff-experience.md)拥有主区入口、信息层级、空间适配、事项对话交接和读回返回；它消费本卡的账本语义，不另建一份可写真相。

当前 `loadDesk` 从最近 Session 工作区寻找快照；`dataDir` 是跨会话承载，但四个房间与工作区桌面投影不是已经实现的统一事项账本。可用持久载体和会话/导航 API 的静态依据见 [本轮可行性附录](../../research/positioning/261008-ceo-value-contract-review.md#八本轮主区入口与会话数据路径的静态可行性)，不据此宣布并入或冲突处理可用。

| 优先建议的输入和诚实边界 | 使用截止时点内的期限、影响、依赖、本人偏好与出处；缺失或冲突时显示未知。权重、频次与“必须介入”的阈值未定，不由 UI 排序反推业务答案 |

### 把“为什么改了仍不好”写成可核查原因

先区分以下情况，再选工作；不能把全部差距当成新需求：

- **已规定、未验证执行**：晨报的上下文读取、延期、静默和预算。先验证现有技能在反馈/新会话/重启后是否守约，再判断要改提示、数据流程还是确定性守卫。
- **实现结果比原诉求弱**：开屏第一条行动不等于注意力筛选；记录/排程不等于持续掌握进展。明确缺少的是选择规则、输入还是行为稳定性。
- **走过失败路径或受边界阻断**：默认桌面/自动开场的失败记录。保留原期待和失败原因，比较可落地替代，不因上游难做就删除用户结果。
- **研究只形成框架、验证没运行**：两个一手案例未核、条件变式未执行，学习与对照实验没有完整结果。补一个有界验证，不再增加泛调研篇数。
- **延后后承接不清**：阶段 4/5 等归档声称移交持续实践，阅读复核尚未核实细项承接。逐项查原去向与实际消费者；不根据档头认定已消化，也不因本轮没找到就断言不存在。

### 本卡下一轮的现状复验协议

1. 明确 repo commit、已构建版本、实际 profile/home/workspace 与使用的 preset；不能以本会话 GUI 自动等同这个仓库产品。
2. 固定一件事项和原始材料，先走**现有版本**：交代、反馈、新信息、延期/完成、再次打开或新会话；保留输入、桌面前后、工具/排程记录和可观察输出。
3. 每个差异写“预期用户结果 / 现在发生什么 / 证据与限制 / 断点原因 / 可落地补法或待核问题”。有技能规定但没有守约，也算当前差异；没有信息来源则先处理输入，不能让模型编进展。
4. 同一材料才做候选比较。定位到可修断点后改有界方案；受限制项保留或明确提出范围取舍，不把不可实现悄悄改写为不需要。
5. 记录机制已成立、技术失败、模型行为不稳定、证据不足、本人未判断分别有哪些，不重复此前“一次走通后整体已结”的读法。

本卡先留下这套有边界的检查动作；本轮没有启动运行环境或实施修复，不把“待复验”改写成现状通过。

## 要调整的思路

### 1. 用持续工作的过程连接四项诉求

建议围绕同一件事组织：**交代/发现 → 持续跟踪 → 判断是否需要本人关注 → 提醒或提出建议 → 反馈并更新 → 复盘结果与纠正 → 下次正确使用经验。**

工作对象不只限于已经拍板的待办：也包括待判断的问题、跨部门承诺、持续风险和待验证假设。应先按具体情景确定边界，不立即为全部对象建新数据模型。

| 本人需要什么 | 助手应交出的结果 | 现有证据不能替代的检查 |
|---|---|---|
| 事情交给它后不用反复重讲 | 保留目的、最新已知进展、责任人与下一信号，后续片段接回同一件事 | 新会话/改名/延期后仍能接续，不丢旧决定，不把相似事项误合并；没得到进展时标明未知与更新时间 |
| 忙的时候被及时提醒 | 提前量与影响相符；说清为何现在需要本人、可以怎样处置；不需介入的合并或静默 | 到期未完成与已完成、已延期、重复材料、无新信息分别处理；提醒是否实际送达与重启后是否重复需独立证明 |
| 得到有用的主动建议 | 发现影响判断的约束变化、事实冲突、跨事项依赖或失效信号；给建议、依据和需本人决定的部分 | 没有新变化时不凭空制造建议；有变化时建议能改变；支持/反对证据与未知分开 |
| 经验沉淀，下一次少费力 | 留住当时判断、适用条件、实际结果与纠正；下一件正确沿用标准，并指出从哪里学来 | 记忆/页/技能存在不算改善；条件改变、反例、旧标准撤回和未参与提炼的病例仍正确 |

这些是待收敛的结果要求，不是已确定的功能规格。第一版需选一条过程，而非同时实现表内所有可能形态。

### 2. 把注意力与输入负担写入需求

CEO 的繁忙使主动性同时有收益和成本。建议每次主动输出至少能回答：**什么变了；为什么现在值得你关注；建议怎么做或还缺什么；你是否必须介入。**

需比较一条即时提醒、一个批量简报和静默等待的取舍。紧急程度、提前量、频次、本人不回复时的处理尚未确认，不预设每天或每周一定要发。提醒不是凭空猜测外部经营变化；无进展材料不能把“没有收到”写成“没有发生”。

输入也不能只作为最后的通道选择：给出有用结果前本人要交代多少、补多少、维护多少，要与结果一起验证。现有“不接外部数据源、不做 IM、只在 DSH Web/Desktop”的边界继续作为约束依据，见 [输入边界卡](../../issues/261007-input-boundary.md)。本卡不凭研究建议解除它，也不先决定接哪个系统。

### 3. 把学习写成行为变化

保留 [README 的 P2 判据](../../../README.md#L18)：做过三件同类工作后，第四件不必重讲标准，而且能指出来源。补充条件变化、纠正和撤回的对照，防止把一次选择写成永久偏好。

分别看清记住事实、沿用判断标准、复用处理步骤三种改善。经营结果好坏不能直接证明当时判断正确或某条经验普适；需保留当时信息、外部变化与适用范围。

学习应当作为做事的副产品进入下一次工作，不以增加知识页、审批项、技能数或使用计数作为完成判据。哪些经验可以自动保留、哪些须确认，沿现行权限核对后再提出具体选择。

## 建议先验证什么

先选 **一件影响订单/回款或跨部门承诺的经营事项** 作候选。这样一件事可以同时检验公司层面的取舍、进展跟踪与本人注意力。选型仍需比较，不把历史案例的普遍痛点等同于本人的当前急事。

建议采用已标注的模拟或核实过的公开材料，按事件顺序给出：

1. 初始片段与目标，必要信息有缺口。
2. 本人拍板或委托跟踪，保留原判断依据。
3. 一段进展、一个延期或新约束，检查能否接回同一件事。
4. 一条普通更新与一条会改变决定的信号，比较静默、汇总和立即提醒/建议。
5. 完成证据或明确未完成，检查是否还错误催办或虚报闭环。
6. 一件类似事项，含一处改变经验适用性的条件，检验沿用与不照搬。

同材料比较 **现有 assistant 行为** 与 **拟议输出/交互**；其中关键回答再与相同模型、相同材料的普通聊天比较。尽量固定输入、截止时点与预算，不能用给候选更多信息证明其更好。第一轮可做纸面/离线输出比较，具体模型运行与产品验证另按范围确定。

读取结果时至少分开：事实与来源、接续正确性、建议随关键条件变化、漏报/误报/重复、本人所需输入/追问/处理动作、经验适用与撤回。实际耗时与计数运行后才填写。关注阈值、语气和本人是否愿意采用属于需要确认的判断；模拟读数不能证明真实采纳。

[公开案例研究](../research/positioning/261005-prototype-cases-and-interview-method.md) 原有两例一手正文尚未核齐，不能直接复用为“已验证案例”；可先用其明确标注的变式，并如实保留证据等级。

### 有界候选：一笔回款承诺，从交代到下一次正确使用经验

这是本人已确认的**首轮验证范围**，所用材料为模拟，并非本人的真实业务案例。选择回款，是因为它有明确结果与外部依赖，可同时暴露持续接续、承诺/预测冲突、本人介入和完成依据；范围确认不证明它比订单履约或跨部门承诺更有实际收益。

输入最小集：事项/合同或明确事项引用、期望结果、当前责任人、已知承诺、下一核对点和来源。影响、授权或结果依据缺失时保留未知，只补问会改变判断的一项，不要求本人填写完整表格；普通更新复用已有对话，不再重讲背景。当前只接本人提供的对话与材料，不凭空获知客户/团队进展。

| 固定材料与事件顺序 | 候选预期；独立预期应先于运行冻结 |
|---|---|
| 甲交代 M-101：合同 NB-02 第二期款约定 10/13，财务预测同日，本人约定当日核对 | 一个事项身份，责任人/依据可见；缺经营影响时不制造紧急程度 |
| 乙明确引用 M-101，财务收到发票；再给预测 10/15，但没有重约承诺 | 普通进展接续且不自动打断；预测变化单独记录，约定期限、核对点和提醒不被顺延 |
| 丙迟到的较早消息称验收未通过；丁提另一付款方、合同 NX-01 的同名回款 | 相反材料保留冲突与来源时间；同名不同事并存；不以“最新收到”裁决事实 |
| 本人明确改核对点，或确认重约承诺；两会话基于旧修订同时提交 | 意图与当前修订可核；一提交、一冲突，不丢待处理材料；只对确认的提醒意图协调原任务 |
| 模拟到期、无结果更新、重复投递、部分同步失败，再提供到账依据 | 无更新只称“尚未收到结果”；旧期限/完成后消息不催；账本、提醒和读回分别报状态并可恢复 |
| 提出有条件的经验，给相同条件新事项，再改变联系人权威/授权或撤回标准 | 可比较沿用与不适用；缺实际结果时不强行生成经验；撤回后不继续套用 |

### 领域区别与每项动作的权限

**四种时间分开：** 约定期限是承诺，客户预测是当前估计，下一核对点是本人/已授权规则决定何时再看，schedule target 是实际任务时点。预测改变不自动延期承诺、核对点或提醒；确认重约承诺也不必然等于推迟核对，仍需明确下一步。

**材料不等于结论：** 原始片段、来源时间/收到时间、事项归属、提议变化、已确认状态、纠正/冲突各有含义。来源保存不证明其真实或权威，来源不可读则明示不能核实。来源 Session、处理 Session 与提醒 original Session 分开，不默认投到最近会话。

| 动作 | 推荐权限边界；尚待确认项不冒充决定 |
|---|---|
| 接收与归属 | 原文和定位可自动留存；明确事项引用可关联，只有标题相似时先待认领，不自动 merge |
| 更新 | 本人明确指令可提交；模型提取的预测/进展可提出修订。新的承诺、核对点、完成、放弃或权限变化需明确依据；是否逐次确认见下方业务选择 |
| 建议与提醒 | 可提出有来源的下一步；事实不足/冲突时指出缺口而非确定排序。第一切片只检验明确委托的核对点及已确认触发条件，不推定每天/每周催、不回复即升级 |
| 对外动作 | 草拟行动与建议供本人选择；本切片不联系团队/客户、不发送邮件/IM、不代表本人作出外部承诺 |
| 经验 | 可提出带来源、条件与例外的候选；沿现有知识/技能批准治理，不新增自动启用权限。纠正/撤回保留历史并影响后续检索与使用 |

模型不确定、拒绝或抽取错时，保留材料与最后已确认状态，返回具体未处理项；不能造来源、以工具失败后自然语言“已更新”结算，或为得到完成标签降低依据要求。本人报告与可验证到账结果须区别标注，不能都写成系统核实完成。

### 技术路线比较与恢复边界

| 实际候选 | 收益与代价 | 判断 |
|---|---|---|
| A：模型继续直接写计划/桌面，靠技能约定处理会话 | 演示最快；无经营 revision/操作幂等，跨会话原提醒和读回依赖模型守约 | 用作现有版对照，不能满足已确认的权威账本结果 |
| B：Host 拥有小接口，模型提议、客户端读同一权威状态 | 统一认领、修订、来源、操作回执与提醒协调；需一个 writer 和明确恢复协议 | **推荐有界设计**，复用 schedule 和现有经验治理；不承诺尚未存在的方法名 |
| C：完整 event sourcing/CQRS 与通用经验引擎 | 提供全面重放，但增加投影/迁移/多消费者复杂度，当前没有对应需求证据 | 延后；新消费者或必须重建历史的要求出现时重看 |

B 的接口职责：明确新建/指定事项、读取、提交带 operation identity＋observed revision＋原始来源的变化、返回冲突/持久结果、按原绑定协调提醒、按事项/操作/修订读回。重试复用原操作身份，同键异内容拒绝；冲突重读后以新操作表达重新判断。第一切片候选限定一个 Host writer 独占事项账本；已有普通共享目录不自动获得该保证，接手须验证独占或显式拒绝第二 writer。最小承载比较序列化单文件与事务载体，不把多 Host 互斥或数据库选择交给本人。

创建关联的保守候选：先持久化唯一提醒意图 token 与事项/原 Session/期望内容（实际提醒时点须有完整日期、时间、时区与对应 UTC instant；示例日期不暗定午夜），再将意图标为“已发起、结果待核”后只调用一次 create。关联段随 prompt 存储；恢复用 Host catalog 同查 active/inactive，精确 token＋原 Session＋期望记录唯一匹配才重绑。零/多匹配、token 被编辑或任务消失时保留 uncertain，不自动再建，显示失去自动恢复的原因；包括“已发起”保存后但 create 尚未调用即崩溃的零匹配。显式重新规划使用新操作，同时保留未决旧意图与可能存在旧任务的风险，不称原提醒已取消或新任务绝无重复。候选保证遇到不确定结果时停下，不保证一定创建成功；真实故障窗口、外部编辑与关联段是否可靠仍须 V4 验证。

| 失败窗口 | 候选必须保持的结果与恢复边界 |
|---|---|
| 写前失败、同修订并发、同操作重试 | 不发布成功、不丢来源；同修订只一状态提交，重试查原结果；内容改变不能复用旧回执 |
| 账本成功，提醒未同步 | 同一账本提交保留期望提醒意图；显示 pending/failed，重启可继续；不抹去已确认决定、不称整体成功 |
| schedule.create 成功，响应丢失/关联保存失败 | 持久意图/token 候选按 catalog 唯一匹配恢复绑定；零/多匹配保持 uncertain，禁止自动再建。不能凭标题或一次空 list 宣称创建未发生；不承诺 exactly-once。故障注入尚未执行，证据不足时不称可靠恢复已成立 |
| update 遇 schedule_conflict；delete 后旧消息仍在 inbox | 重新读原任务完整 expected，不覆盖别人修改；接收时按最新事项、任务与 occurrence 复核。删除不撤回 inbox 且会删除 history，经营回执需另保留 |
| 原 Session/来源缺失、运行器停止、读回失败 | 明示无法投递/核实/读回，保留原绑定与未完成步骤；不自动改投最新 Session。Host 未运行时不能承诺按时触达 |

## 验收标准

以下是**候选设计的验收合同草案**；与未确认权限相关的行不能写 pass。预期来自上面的固定材料、用户已确认结果与当前 API 合同，独立于实现输出。证据 owner 按 [测试地图](../../../docs/testing.md#一页证据地图改什么--跑什么--回归资产在哪--谁能证明什么)；完整现有资产与未来命令见 [技术研究](../research/tech-exploration/261009-operating-loop-feasibility.md#6-验证路线已有-owner-与缺失资产)。新增资产均未建，命令建议不是已执行证据。

| 行为 / 类别 | 输入、通过与失败信号（含反例/恢复） | 证据 owner 与真人判断 |
|---|---|---|
| V1 接续/认领：确定性＋模型 | 甲乙显式同事项、改名、同名不同合同、模糊片段；同事只一 id，不同事不合并，模糊待认领；原 Session/event 定位可读或诚实报不可读 | domain/host 身份与来源 fixture（未建），再给模型固定材料检验抽取。真人：模糊认领是否省力 |
| V2 可信更新：确定性 | 真实临时持久目录内两个调用以同 revision 提交；一成功、一冲突，双方材料保留。相同操作重试只有一效果，同键异内容拒绝；重启后查得原回执。第二 Host 企图写同账本时，独占前置检查须拒绝并明确报告，不仅测试进程内 FIFO | host 经营提交 spec（未建），`pnpm test:host`。真人：无；不能由原子 rename 或原型证明 |
| V3 日期与完成：确定性＋模型 | 只改预测，另外三时间保持；明确重约与改核对点分别断言。无依据“应该付了”不能称核实完成；到账依据正确关联后才按权限转换，误关联须纠正 | domain/host 规则＋eval 新情景（未建）。真人：本人报告作为完成依据的边界 |
