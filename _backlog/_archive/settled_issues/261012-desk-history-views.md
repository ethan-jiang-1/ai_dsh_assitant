# 推敲：桌面历史视角——账本「做过的事」的呈现（传记/过滤/流水）

> 立卡：2026-10-12 ｜ 状态：已结（2026-10-12 关闭）｜ 类型：Feature ｜ 可关闭：是 ｜ 结论：三切片同轮落地（传记段/过滤 chips/流水视角＋命令入口），claim+flow 双场景 e2e 全绿含流水相位，本人在真实账本上实走认领后通道清空；延后项（搜索、分页）句子住[规格卡](../../../notes/implemented/2026-10-06-desk-operating-entry.md)验收台账

**问题与期望结果：** 本人提出（2026-10-12）：桌面上只呈现「没做的事」（在办＋待认领，盯的视角），**做过的事情没有查回来的手段**，靠对话查既不确定也不免费。期望＝桌面上有确定性的历史呈现面：按事项看它怎么走到今天、按状态筛已了结的、按时间看我做过的所有事。

**当前情况（已核实，2026-10-12）：**
- 历史数据早已全量存在：账本 `operations` 是完整审计流水——每个动作带语义类型（交代/记录进展/确认改期/拒绝提案/认领/办结/放弃）、来源会话、原话引文、时间戳、结果回执；单 writer 权威、跨会话共享。
- 更进一步：这本流水**已经整本投影到客户端**（投影的平铺回执即读回单元），桌面只是没渲染；已办结/已放弃事项也已在列表里（K2 验过「7 在办＋1 完成」夹具），只是与在办混排、被「盯」的编排淹没。
- 结论：**缺的不是数据，是一个呈现视角**——查历史是渲染问题，不是模型问题。DSH 原生面已查：轨迹 panel 与 session-search 的语料是会话日志（聊天记录），跨会话的经营事实在单个会话里看不全——这正是账本存在的理由，账本流水才是「做过的事」的正身。

## 方案与取舍（2026-10-12 推敲深化：UX 逐点定案）

**信息架构：桌面两个顶层视角——`看板`（默认，盯）与 `流水`（查）。** 历史不另立面板、不进右侧栏：账本的唯一家是桌面（会话桌退役的既有决定），碎片化视角只会分裂心智模型。视角状态进 `ProjectionView`（`mode: 'board' | 'activity'`），与选择状态一样跨面板切换存活；流水视角进入时回到顶部，滚动位置记忆只在看板模式生效（一个滚存记录，不按模式各存一份——YAGNI）。

**视角一：看板（现有 surface + 过滤 chips）。** 列表头加过滤 chips `全部 | 在办 | 已了结`，默认**全部**（对现状零回归；已 K2 验过的列表行为不变），已了结＝办结＋放弃。待认领卡不受事项过滤影响（它们是收件箱，不是事项状态）。备选口味：默认「在办」让盯更锐——留本人反转，先取零回归。

**视角二：详情页「动作」段（每件事的传记）。** 详情页在「依据」（材料=输入）之后加「动作」段（操作=决策），倒序：人类标签＋本地时间＋来源引文（clamp 两行、点击展开——DeliveryHistory 的习语）＋来源会话。**刻意不把材料与操作交织成一条时间线**：材料已在依据段完整在场，交织即重复；两段各司其职。操作必有 `entrust` 起步，该段恒有内容。

**视角三：流水（全局活动流）。** 全部操作倒序、按查看者本地日期分组（日期头 `10月12日 周一`，条目 `HH:mm`——复用 `humanTime` 的本地化路径）；每条＝动作标签＋事项标题（点击→`selectMatter` 跳转并选中）＋引文 clamp；retained 片段的到达也是一条（「收到待认领片段」），流水于是完整覆盖「进料」与「动作」。渐进揭示：账本已整本在客户端，**「显示更早」是纯客户端翻页，零新传输**——DeliveryHistory 的游标 RPC 形态在此量级是不必要的复杂度。空态诚实：「还没有做过任何动作——交代第一件事试试」。

**DSH 插件力的四个接入点：**
1. **命令面板（commandUi）**：新增贡献「打开桌面·流水」——本包已有 rooms-as-commands 先例（知识室/记忆室的 `/`与`+` 发现面），run＝`selectPanel('dsh-smart-assistant-dashboard')`＋置 mode。历史检索由此获得键盘可达的发现面。
2. **DeliveryHistory 习语**（vendor schedule 面板的交付历史）：newest-first、渐进揭示、长引文 clamp＋展开——照抄形态，不引它的 RPC（我们无需传输）。
3. **`ui-primitives/relativeTime`** 作平台参考；本面板刻意不引 vendor React 组件（面板是 `ce` 直构＋自包含样式，引 primitives 会把 React 组件树拖进独立 bundle）——日期头用本地日期而非相对时间，历史要的是确定性坐标不是「3 分钟前」。
4. **30s 周期刷新已存在**——流水随账本变动保持 live，无需新订阅。

**标签词表（客户端显示串）**：entrust 交办立项 / report 记录进展 / revise 修订 / propose 提出请示 / confirm 确认 / reject 拒绝 / note 记一笔 / claim 认领归户 / complete 办结 / reopen 重开 / retained 收到待认领片段。强调色只给三个：办结(success)、放弃(abandoned)、请示(warn)——历史是阅读面，不是告警面。

**输掉的方案（推敲深化后累计六条）：**
- ① **用会话轨迹/会话搜索查账本史**——语料错位（聊天记录≠经营事实，单会话看不全正是账本存在的理由）；
- ② **服务端全文检索（FTS）**——投影已整本在手、量级未到，过度预建；
- ③ **第二份「历史存储」**——违反单 writer 原则，历史就是 operations 本身；
- ④ **材料与操作交织成单一时间线**——材料已在依据段完整在场，交织即重复渲染，传记信息量不变而噪音翻倍；
- ⑤ **历史进右侧栏独立 tab**——账本视角碎片化；会话桌退役时已定「唯一桌面＝主区账本桌面」；
- ⑥ **服务端游标分页 RPC（照抄 DeliveryHistory 的传输层）**——单 writer 量级未到，投影整本在手，客户端翻页即可；byte cap 撞上再升级（触发已记）。

## 已知与未决

- 投影回执现无 `kind`（`flattenOutcome` 丢弃了操作语义）——切片①的域层改动点，additive 不 bump envelope（客户端解析器 spread 透传已核实）。
- 远期 concern：流水随时间增长会撞投影 byte cap——届时分页，现在不动（触发＝真的撞了）。
- 搜索框延后：客户端过滤在几十件量级足够；量级长大了再谈检索（可挂进流水视角的过滤，不影响本卡切片）。
