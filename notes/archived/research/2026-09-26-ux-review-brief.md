## English abstract (for a reviewer who does not read Chinese)

I need a UX/UI critique of a **"cultivation surface"** for a CEO's digital-twin assistant (a DSH plugin).
Three panels — *My Desk* (what needs you / what's in flight), *Knowledge room*, *Memory room* — shown either
as a full page or, primarily, as a **narrow tab beside the chat**. Data comes from a JSON file the assistant
writes; **every button in the panel is actually a prompt sent to an LLM**, which then edits data and rewrites
the file (asynchronous, seconds to minutes, can fail). The single real user reaction so far was: *"I can see
the desk, and I can see a pile of stuff… I come to this desk and what exactly am I supposed to do?"* — my
response was a "Start here" lead card, which is still unvalidated. I cannot see the rendered UI (no browser
here), so every visual judgement so far is inference from code. Sections §4 (platform constraints), §5 (my
honest confusions) and §6 (what feedback helps) are the parts I most want read. The full brief is in Chinese
below — ask the requester for a translation of any section.

## 1. 产品与使用者

- **产品**：一个 DSH 插件（`dsh-smart-assistant`），做**中小企业 CEO/VP 的数字分身**：管理岗基座 +
  跟本人配合即学进去。它有一个跨会话的 working folder（记忆 / 探索线索 / 知识页 / 技能）。
- **使用者画像**：CEO 本人。非重度软件用户、碎片时间、要在几秒内判断"现在要不要我出手"。
  他的原话定义了立场：**"助手有时候昏的话，至少能指出来你这玩意在哪儿弄错了。要培养数字分身啊。"**
- **被评审的东西＝"培养面"**：让本人**看见助手此刻的判断**、并**在看见的地方直接处置**的界面。

## 2. 被评审的面：现在长什么样

**三室**（内容分工：一个事实一个家）：

| 室 | 放什么 |
|---|---|
| 我的桌面 | 行动面：从这开始（引导卡）→ 在办的事 → 已办 → 缺什么 → 在跟的事 → 它最近做了什么 → 规模 |
| 知识室 | 它懂什么：待审批草稿 → 已确认 → 已退役 → 技能（随包/学来的） |
| 记忆室 | 它记住了你什么：全量记忆，按"关于你的偏好/你的决定/事实/其它"分组，每条带出处与"这条记错了" |

**两个形态**：①主区域整页（左栏图标点开，宽，maxWidth 620px）；②**右侧栏 tab**（紧挨对话，
窄栏；用户 2026-09-26 拍板这是主形态，因为它顺手拿到会话 id、且"培养时随手指错"的姿势就在对话旁边）。

**桌面窄栏的实际结构（我按代码画的草图，不是截图）**：

```text
┌─ 右栏 tab（紧挨对话，窄）──────────┐
│ [我的桌面]                          │ ← tab chip 由平台渲染
├─────────────────────────────────────┤
│ 我的桌面                            │ ← h2 18px
│ [刷新桌面] [在对话旁打开]            │
│ [回顾一下] [体检]                    │ ← 快捷操作
│                                     │
│ 从这开始                             │ ← 分区标题 13px 灰
│ ┌─────────────────────────────────┐ │
│ │ 先办这件                         │ │ ← 11px teal
│ │ 季末最后 4 天是否允许例外签单？    │ │ ← 16px 加粗
│ │ 这是只有你能拍的判断……            │ │ ← 12px 灰
│ │ [回答] [看选项]                  │ │
│ └─────────────────────────────────┘ │ ← teal 边框 + 浅底
│ [等你决定（还有 4 条）]              │ ← 折叠其余决定
│                                     │
│ 在办的事（5）                        │
│ · 把 20% 归到客户/单……               │ ← 13px
│   负责人：CFO · 时点：10-02 前        │ ← 12px 灰
│   度量：闭合到 ±2pp                  │ ← 11px 灰
│   停止条件：……                       │ ← 11px 灰
│   [改这条] [办完了] [不办了]          │ ← 11px 按钮
│   …（其余四条同构）                   │
│                                     │
│ 已办（1）                            │
│ ✓ 定死「20%」的口径与范围……          │ ← 灰、无按钮
│                                     │
│ 缺什么 / 在跟的事 / 它最近做了什么     │ ← 各自成段
│ 我记住的规模  记忆 7 知识 13 技能 3   │
│ 读自 <工作区路径> 的 .desk/state.json │ ← 出处行
└─────────────────────────────────────┘
```

**数据流（理解这套 UI 的关键，请务必读这一段）**：

1. 助手（大模型）自己把状态写进**会话工作区**的 `.desk/state.json`（它用文件工具写，不是面板写）；
2. 面板**只读**这个文件（经平台的一个只读文件通道）；
3. 用户在面板上的**每一个动作都是一条发给模型的聊天消息**（例如点"办完了"→ 发送"行动「…」已经办完了。
   请记录结果……完成后加载 desk-refresh 技能，把桌面文件重写一遍。"）；
4. 模型处理（10 秒~几分钟，可能失败、可能理解得不一样），改数据、重写文件；面板延迟重读，界面才更新。

**所以：这里的"按钮"是提示词，"提交"是异步且不确定的，"数据库"是模型自己维护的一个 JSON 文件。**
（这不是偷懒，是平台约束下的唯一通路：本插件在平台构建期清单之外，开不了自己的数据通道——见 §4。）

## 3. 已有的真实证据（不多，但都是真的）

- **唯一一条真人反馈原话**（2026-09-26，CEO 本人第一次打开桌面）：
  > "这样我能够成功地看到桌面，然后能看到一堆东西。你说哪里别扭？……我跑到这个桌面上，你让我到底要干什么呢。"
- **我的解读**：桌面长成了**审计清单**，没长成**行动面**；等权重的行堆＝没有入口。
- **我的回应（尚未被验证）**：「先办这件」引导卡——第一条决定升格为大字卡，其余决定默认折叠。
- **已经跑通的一圈**（同一晚，真人继续用）：他经面板完成了 4 次真实处置（要选项、办完了、不办了…），
  助手逐条接住、改了数据、重写了文件——**循环本身成立**。
- **实测到的第一个摩擦**：他对着同一个决定**连点了 3 次**"看选项"（因为点击后界面几乎没反馈，
  而回答出现在**对话里**、桌面上没有痕迹）。已改为：忙时冻结全部按钮 + 明说"回复出现在对话里，
  桌面在它刷新后自动跟上"。
- **还没验证的**：引导卡（他没再看）、窄栏里的实际观感（我从没见过渲染结果）、三室划分是否合用。

## 4. 平台约束（DSH 很新；这节决定"什么能做、什么做不了"）

DSH 是一个 agent harness（模型 + 工具 + 插件组合）带 Web UI；插件分 host 面（服务/工具，模型可见）
与 **client 面**（浏览器 UI，模型不可见）。被评审的是 client 面。硬约束：

- **client 代码是 classic script**：不能有 `import`/`export`（一条就炸掉整条打包组合），只能经页面全局
  `__ModuleLoader__.load({...})` 注册；React 经模块表 `require('react')` 拿。
- **一切可见面走 slot 系统**：`inject(座位名, () => register(声明, 组件))`。可占的座位由平台定义
  （左栏图标列、主区域、右侧栏 tab、会话页头工具位等）——**不能自己造座位、不能改平台布局骨架**。
- **不能加第三方依赖**（仓库纪律"只借思路不装包"）；**样式是内联样式 + 硬编码颜色**，尚未接入平台的
  设计 token / primitives 组件库（接不接、值不值得接，也是待评审的问题之一）。
- **右侧栏宽度由平台决定**（我没量过具体像素，只知道是窄栏）；tab 的 chip/标题由平台渲染。
- **面板是 per-session 的**：每个会话一个实例，读该会话工作区的文件；跨会话不共享。
- **我能改的**：面板内部的一切（信息架构、分区、层级、组件、文案、交互），发给模型的动作提示词，
  以及模型面技能（它决定"助手往桌上放什么数据"）。

## 5. 我的困惑（**最想听你意见的部分**，编号便于你逐条回）

1. **信息架构**：三室（桌面/知识室/记忆室）是不是把**助手的内部数据模型泄漏成了用户的心智模型**？
   CEO 的心智可能不是"记忆/知识"，而是"你在跟我的哪件事/等我什么/最近干了什么"。有没有更好的切法
   （按任务？按时间线？单一 feed + 过滤？）——三室该合并、该改名，还是该保留？
2. **"一次一件事" vs "全都在"**：引导卡是对"一堆东西"的回应，但它把其余决定**藏**起来了。
   对 CEO，藏起来是帮忙还是添乱？平衡点在哪（几条展开？折叠的提示怎么写？）
3. **打字摩擦**：所有处置都要**打字**（更正内容、决定答案）。对 CEO 这个人群可接受吗？
   有更省的形态吗？（预设选项？语音？一键"不对"+模型追问？拖拽？）
   注意一个硬信息：模型需要知道"什么是对的"，完全零输入可能做不到——那最小输入是什么？
4. **LLM 异步性**：按钮＝给模型发消息，慢、可能失败、可能做得和你说得不一样。UI 该怎么表达
   "进行中/完成/失败/它做了别的"？现在是"冻结 + 一行说明 + 自动重读"。有没有更好的模式
   （收件箱式回执？乐观 UI？每次动作留一条可核对的结果条？）
5. **信任与核验**：面板显示的是**助手自述**的状态（它自己写的文件，没人验证过）。怎么让"这是真的吗"
   变便宜？现在是每条带出处 + 新鲜度告警（"对话比这份桌面新…"）。够吗？"助手说" vs "已验证"的
   视觉语言该怎么设计？
6. **密度与排版**：13px 正文 / 11–12px 灰字 meta / teal 边框 / 每行 2–4 行信息——一眼扫读会出什么问题？
   **窄栏（右侧栏）下尤其**。这条我最需要你的眼睛（我看不到渲染，只能从代码推断）。
7. **空态与错态**：助手还没写过文件 / 文件过期 / 动作失败 / 这个会话没有桌面——分别该怎么说话？
8. **该砍什么**：桌面现在有 8 个区块（从这开始/在办/已办/缺什么/在跟/最近做了什么/规模/快捷操作）。
   最小可用的桌面是什么？三室里有没有该合并的？"规模数字"这种信息值得占位置吗？
9. **优先级**：如果只能做三个改动，你做哪三个？
