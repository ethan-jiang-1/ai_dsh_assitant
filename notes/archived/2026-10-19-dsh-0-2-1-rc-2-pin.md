# DSH pin 迁到 `dsh-v0.2.1-rc.2`：三处破坏性变更 + 一次真机端到端

日期：2026-10-19 · 状态：**implemented**
已归档：2026-10-20（pin 迁移记录；当前 pin = vendor/UPSTREAM.md）

## 决定与依据

用户直接要求升到 `dsh-v0.2.1-rc.2`，且明确要求**以端到端为准**收口（"只有端到端测试过了，你才知道东西都没什么问题了"）。本片因此不只跑门禁，还把真 Web 起起来、真发一问、真收到回复。

`vendor/dsh` 从 `dsh-v0.2.0-rc.2`（`639ed015…`，2026-09-29）到 `dsh-v0.2.1-rc.2`（`687f282e…`，2026-10-17，PR #6408）。`vendor/UPSTREAM.md` 三行已由 `sync-dsh` 改写，`dsh.compatibility.dshReleases["0.2.1-rc.2"] = verified` 只在 typecheck 真跑过之后才写。

## 三处破坏性变更（都不是"照着 changelog 改一行"能过的）

| 上游变更 | 我们的踩点 | 处理 |
|---|---|---|
| `working-directory`（alpha.1）：loop 不再注册内建 `{{cwd}}` 提示变量 | persona 行的 `suffix` 里写着 `Your working directory is {{cwd}}.`，**未解析的变量在每次模型请求前就失败** | 删掉该 suffix 整句，改由上游 `working-directory` 服务提供目录事实（日志里已见 `working_directory` 工具） |
| `subagent-activations`（alpha.1）：`tool-subagent` 移除 `backgroundMode` | 我们四行（subagent / fork / codex / claude-code）各带一个 `backgroundMode` | 四个键全删；行本身仍挂载，`subagent`/`subagent_fork` 在真请求里都在 |
| `jsonl-persistence-plugin`（alpha.1）：JSONL 持久化不再有 default 导出 | 组合测试用 `import SessionPersistenceJsonl from …` | 改 `import * as` |
| `plugin-engines-dsh`（alpha.3）：兼容性判定先读 `engines.dsh` | 本包未声明 `engines.dsh`，回落到 peer 规则 → **不被拒**（`release-smoke` 实测通过） | 无需改，记录事实 |

**changelog 之外多踩的一个**：`rpc-host.ts` 的 `createSharedFetchHandler().fetch()` 现在要求第二个参数 `Peer`，且 exact route 对非 owner 直接 403。`desk-projection-lifecycle.spec.mjs` 的 3 个用例因此全红（`Cannot read properties of undefined (reading 'principal')`）。按 `rpc-host.ts:94` 同款构造 owner `Peer` 修好。这条**不在任何升级指南里**，是本片最有价值的发现。

## 三处既有 bug（与升 pin 无关，但这次才撞上）

1. **`repair-vendor-artifacts.mjs` 路径算错**：`resolve(fileURLToPath(import.meta.url), '../../vendor/dsh')` —— `fileURLToPath` 返回文件路径，当相对路径的基准就把脚本自己当目录。该 bug 从脚本搬进 `scripts/maintenance/` 起就存在，因为**这个脚本只在换 pin 时跑**，所以一直没人碰到。修成 `resolve(dirname(...), …)`，并补了两处 import 深度。同类问题在 `typert/generator` 的 import 上也有（`../vendor` → `../../vendor`）。
2. **typecheck 会给出假红**：新 pin 引入新依赖（`ipaddr.js`/`p-limit`/`semver`/`minisearch`），没装时 tsc 在 vendor 源码里报 `Cannot find module`，**看起来和 API drift 一模一样**。首次 `sync-dsh` typecheck 报 20 条，19 条是这个原因。已把 `pnpm install` 固化进 `sync-dsh`（typecheck 之前跑），并在注释里写明为什么顺序不能反。
3. **corepack 版本闸**：vendor 包自己的 `bundle` 脚本经 corepack 运行，`packageManager` 对不上就整批拒绝（`This project is configured to use 11.28.5 of pnpm. Your current pnpm is v11.7.0`）。已把"对齐 pnpm 版本"固化进 `sync-dsh`，带 prove-it-red 测试（去掉逻辑 → 1 红，还原 → 12 绿）。

## 客户端重建：官方入口 + 一个假绿教训

`pnpm verify` 的 `vendor: client faces and web dist are not older than their sources` 判 52 项陈旧（换 pin 必然后果）。

**先踩了一个假绿**：我自己写的循环脚本用 `tail -1` 取"最新源文件"当判据，把 39 个包判成 fresh —— 而门禁仍判红。这正是 `scripts/AGENTS.md` 第 3 条禁止的"判据与门禁不同源"。改用门禁同款 `newestSrcMtime`（递归取全包最新 `.ts/.tsx/.css/.json`）后，真值才出来。**教训：重建脚本的判据必须照抄它要满足的那条门禁，不能自己发明。**

**正确入口是 vendor 自己的脚本**，不是逐包 `run bundle`：

```
tsc -b tsconfig.host.json          # client 入口来自 host 的 lib/types，noEmit 的 client 配置本身不产它
tsdown --env.DSH_BUILD_FACE host   # 跳过末尾 desktop 那步（apps/desktop 刻意不在根 workspace）
tsdown --env.DSH_BUILD_FACE client
pnpm --dir vendor/dsh/apps/web run build   # shell 必须最后
```

一个前提绕了很久：vendor 树有**自己独立的 `node_modules`**（根 workspace 只收 `vendor/dsh/packages/*/*` 等子目录，不含 `vendor/dsh` 本身），而它 9-30 那次是 `--ignore-scripts` 装的，**bin 链接大面积缺失**（72 个 devDeps 只有 5 个 bin），导致 `spawn ENOENT: tsdown`。根因不是代码，是安装残缺；补装一次即好。若日后又见 `tsdown: command not found`，先查 `vendor/dsh/node_modules/.bin/` 的条目数，不要去改构建脚本。

**孤儿产物**：`api/gateway`、`client/connection`、`typert/registry` 三个包新 pin 改产出 `client.node.js` + `client.browser.js`，exports 也不再指向 `lib/client.js`，但旧 pin 留下的 `lib/client.js` 还在（`lib/` 被 gitignore、未跟踪），门禁按 mtime 判陈旧。这不是门禁的错——它守的是"浏览器产物不得旧于源码"，而一个没人引用的旧产物正好是它该报的。删掉即绿。

## 收口后又抓出两个 trap（都由"重建 vendor"引入，都不是升 pin 本身的破坏）

第一次全绿是**在提交前**的运行树上取的。提交后复跑 `pnpm test` 直接红了 6 个用例——原因是我在两者之间重跑过一次 vendor 重建，而 vendor 产物有两处**顺序依赖**：

1. **`llm` 的 `createRequire` 深度**：`src/attribution.ts` 写 `'../package.json'`（对 `src/` 正确）。tsc 把它落到 `lib/types/`（该层需要 `'../../package.json'`，`repair-vendor` 会修），tsdown 又把 `lib/types` 内联进 `lib/index.js`（该层需要 `'../package.json'`）。**先 repair 后重建**，tsdown 就把 deep 路径焊进了 bundle → 任何 import `dsh-llm` 的测试都死在 `Cannot find module '../../package.json'`。已让 fixup 同时覆盖两层，顺序不再有意义。
2. **shim 丢 default**：`lib/index.js` 是 `repair-vendor` 写的转发 shim，原文用 `export *`，注释还断言"这些模块没有 default 导出"。0.2.1 的 `dsh-llm` src 末尾是 `export default LlmRuntime`，而 `export *` **永不转发 default**。症状极具误导性：`typeof LlmRuntime === 'undefined'` → Cordis 抛 `invalid plugin, received undefined`，**栈却指向 `ctx.plugin(Loader)` 那行**（那行完全正常）。靠一行临时 `console.log` 打各导入的实际值才定位。shim 现在从产物里检测 default 并转发。

**教训**：重建 vendor 之后必须 `repair-vendor` 收尾，且**"全绿"的证据只在它所在的那棵产物树上有效**——提交前后各跑一次，才不会被自己中间的重建骗过。

**端到端的权威证据在服务端会话日志里**，不在浏览器里（loop-probe 的 `replyTail` 抓的是 `document.body.textContent` 尾部，撞上 SVG 内容，是取证的局限，不是页面问题）：

```
provider: deepseek-official · model: deepseek-flash
request/header tools: 42 个，含 assistant_{knowledge,memory,operating,reflect,research}
assistant/message: 「收到，你的消息我这边已完整收到——一句话确认：我能收到。」
turn/end: {"turn":1,"reason":{"kind":"completed"}}
```

## 输掉的方案

- **逐包 `pnpm --dir <pkg> run bundle`**：51 包全红（`spawn ENOENT: tsdown`）。每个 `--dir` 都把该包当独立 workspace 根，pnpm 从那里重解析整棵树（实测在重下 235 个包，20-40 KiB/s）。改走 vendor 根脚本一次解决。
- **`pnpm install --force` 修 bin 链接**：跑了 40 分钟无进展（15 分钟零 store 写入），361 个项目全量重取，在慢网下不可控。放弃，改用定向补齐。
- **给门禁加"孤儿产物豁免"**：想过让 freshness 检查忽略 exports 不指向的 `lib/client.js`。放弃——那会把真正该报的"旧产物没清"也一起放过，而删掉三个文件只需一条命令。门禁不动。
- **在共享 dev home 上跑 `web-expected`**：首跑红了 33 行 diff（"默认工作区" vs `ai_dsh_assitant`、"设置" vs "账号菜单"）。读场景 README 才发现该场景**契约要求隔离 home**（共享 home 的"空白态"不空白）。换隔离 home 后只剩 1 行真实漂移。
- **把"设置→账号菜单"当回归**：查 `vendor/dsh/packages/client/ui-settings-account/src/client/locales.ts` 确认 `menu: '账号菜单'` 是 0.2.1 上游文案（`git log` 指向 PR #6408），与本包无关，属预期变化，故重录期望。
- **给本包声明 `engines.dsh` 应对新兼容性闸**：没做。`evaluatePluginCompatibility` 无 `engines.dsh` 时回落到 peer 规则，本包 peer 范围本就覆盖，`release-smoke` 实测接受。多加一个声明等于多一处要跟着 pin 维护的事实。

## 带走的三条

1. **重建脚本的判据必须与门禁同源**——自己发明的"最新文件"会在慢钟/多文件时假绿。
2. **vendor 的构建入口是它自己的 `scripts`**（`build:lib:*` / `build:web`），不是逐包 `run bundle`；后者既丢 PATH 又重解析依赖图。
3. **端到端不可省**：前三层（typecheck/test/release-smoke）全绿时，真机上仍有 `{{cwd}}` 这类只在"请求组装"那一步才炸的问题。`--dump-config` 也看不见它——只有真发一次请求才会暴露。
