# desk 摘要带 pending 提案索引：让"一次 desk 读"能列出简报该列的行

日期：2026-10-16 · 状态：**implemented**

## 问题（可观察行为）

**外部结果三要素：** 触发＝本人让助手建每日简报（或任何"按点读一遍桌上经营事项"的常态汇报）；本人得到＝**一份简报里能看到"有事在等你拍板"**，而不是只看到进度、漏掉唯一需要自己决定的东西；完成条件＝`assistant_operating action=desk` 的摘要带出每件事的 pending 提案，简报能用**一次 desk 读**列全它清单上的行，且措辞不把未生效的提案说成既成事实。

**为什么它是决策面**（两条合同事实）：[`docs/operating.md`](../../docs/operating.md) §权限三分——模型推断的重大变化**不直接生效**，只走提案，pending 提案是账本里**唯一必须本人拍板**的东西；同文件 §返回契约——绑定会话在绑定后为该事项创建的任一 pending 提案**阻止返回**，一件可能**卡在等人确认**的事，简报不提它，本人永远不知道有事在等自己。

**缺口是被什么咬出来的**：晨报的 web 回归资产（[`dev/probes/web/desk-daily-brief-live.mjs`](../../dev/probes/web/desk-daily-brief-live.mjs)）第一次真跑就报出来——那次 desk 读的载荷（实测 951 字）只有事项与未归属片段，`p-1`/`pending`/`proposal` 全无；真模型于是没列它，同时**正确**列出了工具真有的「逾期无新进展」与「待认领片段」——不是模型偷懒，是摘要没给。

## 还会约束以后的后果

- **pending 在板子上、已解决只在 `read`**：板子的语义是"要你拍板的"，不是历史；以后加投影行按这条分工。
- **未生效的变更必须在文本里说出来**：模型读的就是这段文本，`pending — NOT in effect …` 是合同（spec 钉住），不是修辞。
- **判据钉账本事实，不钉模型措辞**：探针的标记集被模型改写咬过三次（日期写法、标题拆词），标记只取账本里的事实词（如 `预付款` 而非标题整串）。
- **新增文件后把 `git add` 放回 `verify` 之前**：链接语料只收已跟踪文件，否则新文件里的链接错会漏掉一整轮（本片立卡时正是这么漏的一处）。

## 输掉的方案

- **B：改技能清单措辞，删掉"等你确认的提案"这一行**。省事，但删的是这个功能的决策面：pending 提案是唯一需要本人拍板的东西，而且会**阻塞事项返回**——简报不提它，等于让卡住的事静默留在桌上。触发条件（若将来真要走 B）：本人明确表示简报只做进度播报、提案走桌面看。
- **A′：只给计数（`1 pending proposal (p-1)`），详情全靠模型自己 `read` 每件事**。摘要最省，但"逐条给默认动作"要多 N 次读，且模型漏读就是漏报——日报的价值是一次廉价扫描（技能原本的设计就是"一次读全量"）。留作摘要体积真成问题时的收缩方向。
- **扩投影 `ProjectionProposal` 带 `change`，让给 Web 客户端的那份投影也带上**：动的是更大的契约面，而 UI 并不需要这个值；改 `deskItem` 所在的账本记录层即可，投影不动。
- **让 `read` 承担全部（desk 不索引，模型逐件读）**：把覆盖率交给模型的自觉，等于把简报的完整性押在 N 次调用上——回归资产里也没法钉"该读的读了"。
- **新增 `DeskItem.pending_proposals` 字段**（立卡时的计划）：实现面发现渲染层早有提案行，复用既有字段更小、且避免两种拼法。
