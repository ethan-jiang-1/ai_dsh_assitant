# 首屏归属：桌面是第一印象，门进会话，刷新回到上次那一面

## 问题（可观察行为）

产品打开时那一屏由本包 dashboard 先选占住，工作区门渲染在 dashboard 里面，于是：

- 点「新会话」绕过门：会话落在 DSH 首启自建的默认工作区，交付包也跟着落在那里；
- 每次刷新都被拽回桌面/门，哪怕刚才正在一段对话里；
- 桌面优先靠的是共享、无仲裁的 `main` 面板选择，别的插件也能在启动时自选。

## 决定

1. **首屏归属：桌面仍是第一印象**（第一次打开 = 「今天」），之后按"上次主视图"恢复：偏好=会话就不选面板，
   平台自己恢复 Session；偏好=桌面才选面板。偏好只存视图（浏览器 `dsha:main-view`），不存业务数据。
2. **门进会话**：未绑定/恢复态下，每个 Session 的 composer 由 `ctx.conversation.blocks` 禁用，
   `conversation.input.dock` 给出原因与项目选择按钮。桌面那份门继续管桌面自己的输入车道。
3. **未绑定不许开聊**：没有"稍后"——它会解锁桌面的第二条输入车道，使门重新只覆盖一条路径。
4. **强制层级**：v1 只做客户端 affordance（平台自己也把 blocks 定义为 affordance）；Host `agent/pre-step`
   反绕过是延后项，触发 = 出现不经 composer 的 prompt 车道真的把回合发到未绑定工作区，或要"机械保证"。

## 输掉的方案

- **A' 会话优先**：最贴平台默认，但把首屏身份从一页纸换成空白会话，反转
  [首开体验：一页纸](2026-10-23-first-run-one-page.md) 与
  [三层界面重排](2026-10-24-interface-layer-rearrangement.md) 的"主面板默认一页纸、会话是编辑层"。
  覆盖缺陷不需要用产品模型反转来修；桌面用户也会反过来被至今最怕的那次刷新拽走（对称损伤）。
- **C 未绑定桌面、绑定后会话**：多一次首屏切换，选桌面还依赖异步绑定结果；收益只是首跑看配置页，
  会话内的门照样要建。
- **D 工作台型**：要改外壳、抢 `main`、收 Chat，是画布型产品，不是本产品。
- **只修桌面门、不加会话门**（原 B）：E4-2 实测绕过，未绑定也能聊。
- **删掉 DSH 自建的默认工作区**：跟平台打架，且下次冷启动还会重建。
- **用 `settings.onboarding` 弹窗挡全屏**：排在平台自己的 welcome-notice 后面，且挡不住侧栏的新会话。
- **Host `agent/pre-step` 拒绝所有未绑定回合**：会让 dev/probe 的未绑定会话一起停摆，要额外给
  8 个场景开 `onboarding: false` 的口子；收益只是堵非 UI 旁路。

## 后果与边界

- 桌面首屏仍依赖 `selectPanel`（共享、无仲裁）；门在会话里兜底，风险是"首屏可能不是桌"，不再是"未绑定能聊"。
- 非产品部署（`assistant-product.onboarding: false`、无入口行、404、传输失败）保持透明：不画门、不禁输入。
- 刷新行为是产品级偏好：换端口/换浏览器会丢（localStorage 按 origin）；首次仍落在桌面。
- 会话仍不能按"门"改 cwd：绑定后从会话 dock 绑定会在新项目开一个新会话，旧的空会话留在默认工作区。
