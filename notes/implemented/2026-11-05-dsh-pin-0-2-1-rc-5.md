# 把 vendor/dsh 钉到 `dsh-v0.2.1-rc.5`

日期：2026-11-05 · 状态：**implemented**

## 决定

`vendor/dsh` 从 `dsh-v0.2.1-rc.2` 移到 `dsh-v0.2.1-rc.5`（精确 SHA 与 tag 提交时间由
[`vendor/UPSTREAM.md`](../../vendor/UPSTREAM.md) 持有，本文件不复制）。动因是与本机已安装的
`@deepseek-ai/dsh@0.2.1-rc.5` 对齐——开发实例与日用 CLI 跑同一平台版本，排障时不必先问
"这是 pin 差还是版本差"。

没有顺带取 `dsh-v0.2.2-rc.1`：它是另一条基线，升它要自己的动因与复核范围；本轮只做对齐。

## 这次升级实际是什么（不是"一个 submodule 而已"）

升级环 = `pnpm sync-dsh -- --tag dsh-v0.2.1-rc.5`：fetch tag → checkout → 写 `vendor/UPSTREAM.md`
→ 装 vendor 依赖 → **typecheck**（API 漂移必须在这里红，而不是运行期）→ 往
`packages/dsh-smart-assistant/release-verification.json` 记一列 verified。

之后还有三件不能漏的事，漏了会静默跑旧代码：

1. **重建 vendor 产物**。`vendor/dsh/**/lib/` 与 `apps/web/dist/` 是 gitignored 构建物，checkout
   不会更新它们；不重建则 vitest 与插件 profile 仍加载旧 pin 的构建物，而运行期启动器走
   `tsconfig.tsx.json` 解析源码——两边不一致时症状是"测试说旧行为、页面说新行为"。
2. **重生成两个派生物**：`tsconfig.tsx.json`（新 pin 多了一个客户端包，运行时解析入口必须跟着动）
   与 `docs/package-catalog.md`（pin 与 verified 列表是它的字段）。
3. **分类提交**：pin 簿记、生成物、note 与依赖锁同 diff，回退时是一个动作。

## 复核后判定不必改的部分

- 依赖的机制仍在：`customSkillDirs`、`dsh.bundle.patch` 装载、`resolveDshHome()` 等按
  `vendor/UPSTREAM.md` 的重审触发表逐条核对，位置未变。
- typecheck 无 API 漂移，本包源码零改动：这次是纯 pin 移动，不是适配。
- `docs/discipline.md` 的继承表不动：没有新机制进入我们借用的那一层。

## 遗留阻断

- `dev-task` 的 headless 冒烟跑不了：本机 **dev home** 的 `.credentials.yaml` 里没有
  `deepseek-official` 路由的可用 key（与本次升级无关，是 dev home 自己的状态；日用 `~/.dsh` 的凭据不共享）。
  Web 实例的 boot + preflight 覆盖了 host/client 行的装载与注册，但"跑一轮真实对话"这件事本轮没有证据。
  补法是给 dev home 配一次 key，之后用 `pnpm dsh --profile dev-task "one task"` 补齐。

## 与"加速"的关系

**升级不是加速项。** 启动耗时由本地工作量构成（setup 的插件安装、boot、preflight），pin 换版本
只是把同样的工作重新编译一遍；pin 一动，tsx 转译缓存失效、vendor 整树重建，**下一次启动反而更慢**
（实测冷转译 boot 明显长于热缓存 boot）。真正的加速来自 `pnpm start` 自己的动作——复用健康实例、
跳过空转的 `dsh plugin add`、以及每步计时——理由与实现见 [`dev/env/start.sh`](../../dev/env/start.sh)
与其判据 [`dev/env/instance.mjs`](../../dev/env/instance.mjs)。

## 输掉的方案

- **裸 `git submodule update` 后直接提交**：submodule 指到了新 commit，但 `lib/` 还是旧的；
  测试与插件 profile 静默跑旧 pin 的构建物，直到某次 boot 才发现"源码和产物对不上"。
- **只升 pin、不重建 web dist**：Web 面会是新旧混合（宿主新、壳旧）。preflight 验的是解析与注册，
  不验行为，很可能仍然绿——问题留到浏览器里，正好是 preflight 想避免的那种。
- **把这次升级当成启动变慢的解法**：启动的耗时点不在平台版本上。选这条路等于用一次跨仓变更
  换一个不存在的收益，还额外引入一次整树重建与缓存冷启动。
- **顺手取 0.2.2-rc.1**：让两件事共用一个变更，回退时无法分辨是哪一步引入的；0.2.2 该有自己的动因。
