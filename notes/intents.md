## 〇、产品初衷（2026-09-25 用户复述；统领下面所有机制意图）

> 这一节补的是**一开始就有、却从未落字**的初衷。I1–I15 都是机制（记忆/技能/知识/家），
> 它们回答"助手靠什么"，没回答"助手替谁、干什么活"；领域缺席后，助手只能学它自己
> （丢失过程见 [总体思路 §1.3](archived/research/2026-09-25-grand-plan-enterprise-expert-assistant.md)）。
> 从此 I1–I15 是本节的手段，判断一个机制值不值得做，先问它推进了 P1–P3 中的哪一条。

**动机**：中小企业的管理者（CEO / VP 一级）经验多，想培养自己的**数字分身**。先有一个
**管理岗基座**——管理、销售、财务等基础技能都有一点，擅长把复杂问题拆开；然后拿这个基座
**跟人配合做几件事，就把东西学进去**，变成这个人的助手。

**用户拍板（2026-09-25）**：

- **立场 = 辅助本人**：帮他想、帮他做；对外发出的东西由他过目，不代表他出面。
- **第一个真人 = 用户本人**（学习效果由他判，不由 agent 自判）。
- **与 `ai_dsh_company` 的关系 = 本仓做基座 + 学习**：它已有的 CEO / VP-Sales / CFO / COO 角色
  技能作为基座内容的来源搬过来（那边有角色、没有"从真人身上学"；本仓有学习机制、没有角色）。
- **第一批一起做的事 = 复杂经营问题的拆解与行动计划**。

**用户拍板（2026-09-28）：基座与现场的分界**：

- 本仓 dev home 的内容（记忆/线索/知识页）＝**基座试车场数据**，可随意处置，**不是本人口味题**——
  摘要预算压力一类问题不再升级为本人的逐条裁决。
- 产品要件＝**到用户手上要能自己学习、自己调整**：家的养护（摘要压力、记忆压缩/改写/退役、
  技能退役）由助手在 hygiene 契约内**自管**，委托人只审品味级与不可逆项。这是出厂能力，不是
  部署后逐项授权。

| P1 | **出厂可用的管理岗基座** | 未学过任何人时，给一个中小企业典型难题（如"下季度销售掉了 20%"），能从管理 / 销售 / 财务视角拆解并给出可执行的行动计划；由用户判"像样" | proposed |

### 〇·三 研发方式（2026-09-27 用户拍板；常设指令落在根 `AGENTS.md`「研发姿态」）

> 用户原话："我是希望这个 REPO 研发宪章这里 1) 尽量遵循 DSH 的研发流程 2) 尽量想办法自主解决问题
> （探索，借鉴成熟 DSH 插件思想尤其是下载量大、影响力够的）3) 阶段感觉可以了不得不让人介入 REVIEW
> 的时候再 REVIEW，别动不动让人 REVIEW，其实有些 REVIEW 你是可以自主做的，是吧？"

三条，都是**判据**（用来判断一次交付的姿态对不对）：

1. **流程随 DSH**：研发流程、门禁、证据阶梯与文档形态沿用 DSH 既有做法，不另造一套。
2. **自主解决优先**：先探索、先找成熟生态的既有解法（读源码抄思路，不装包）；技术/设计选择由 agent
   判定并记理由（note 的「输掉的方案」/判定记录是理由的家），**不把选择推给真人**。
3. **阶段才 REVIEW**：自己能做的审查自己做（代码审查、回归证据、设计自审、真机取证、对抗性自评）；
   只在阶段收尾且**确有真人不可替代的输入**时请人 review——真人输入＝真实业务内容、合规/法务文本、
   产品口味反转。**"等用户拍板"不是默认状态**。

**为什么记在这里**：这条纠正了此前的实际做法（把技术/设计分叉堆成"待你拍板"清单，最长一次列了五项，
用户反馈"我有点不知所措……你自主判断不行吗"）。它约束的是**姿态**，所以判据放本文件、
常设指令放 `AGENTS.md`，两边互指。
