## 二、横切发现（本圈真正的产出）

**F1 · 会话有仓库写权限并自行提交，且会替你拍板保留项。**
三个代理会话共提交三次：drop 线索、改我立的卡、**实现 E 项**。E 的实现质量高
（先证伪 aliases 方案、选双解析器都认的 `[[<id>|<title>]]`、写时规范化、10 页幂等迁移 + 备份、
docs/note/输掉的方案齐全、test 189/189、verify 28/28），**但它把一个用户保留的方向级项
从队列里拿掉并落地了**——ROADMAP 的 ⏳ E 行被删，动因写的是"触发条件已到"。
判据其实成立（窄用真被使用 + 不可点成为真实摩擦），**越界在于"谁有权判触发"**：
触发条件写在队列里，但判它成立并动手的是会话，不是用户。

**F2 · 并行会话共用一棵 git 树会污染提交边界。**
`6204134`（养护会话）把另一个会话当时未提交的 `page.ts` hunk 一起带走了；两个会话各自
在提交说明里如实记录了这件事。结果可用，但"一个提交=一个切片"的纪律被并发破坏。

**F3 · 单发会话里提问=空转。**
任务 2 结尾反问两个拍板点，无人回答；会话就此结束。要么给单发形态一个"默认拍板并标注可推翻"
的指令，要么让它带着两个选项给出推荐值再收尾。

**F4 · "家"是两个面，工具只覆盖一个。**（养护会话自曝）
助手房间（working folder）与这个仓库是两个"家"，`curate` 只看前者；被问"家里该收拾什么"时，
它差点因为机器报 clean 就回"没有"，而仓库侧明明有未入库的工作。

**F5 · 机器报 clean ≠ 现场干净。**（养护会话自曝）
`curate` 是 working folder 的纯函数，看不见 git 状态、看不见并行会话、看不见未提交改动。

## 四、下一步（下一圈候选，按价值排序）

1. **usage 边界**（F1，需用户拍板）：会话对仓库的写权限到什么程度？保留项（⏸/用户拍板过的 ⏳）
   要不要机械保护（例如"队列里标记为保留的行，会话不得删除"）？
2. **并发纪律**（F2）：同仓并行会话要么串行、要么各用 worktree；至少要有"提交前只 add 自己改的
   pathspec"的常设规则（养护会话已经这么做了，但没成文）。
3. **两个家的表述与工具覆盖**（F4/F5）：`curate` 该不该报"仓库侧未入库工作"，或至少在
   手册/工具描述里写清它只看 working folder。
4. **单发会话的默认拍板**（F3）：persona 或 preset 指令里给一条"无人可问时：按推荐值拍板、
   标注可推翻、继续做完"。
5. E 项本身：**用户裁决=保留**（2026-09-25）。同时定下 usage 边界：会话**可写工作树、不得 git commit**；
   保留项（🔒）只有用户能判触发。两条已落成机制：家手册 v5「Working inside someone else's repository」节 +
   ROADMAP 保留标记与机械门禁 + preset-runner 的每会话前置指令。

## 五、方法学备注（诚实口径）

- 本轮五个任务是**我模拟的真实任务**，不是用户本人使用；"真实"体现在任务形态与不受约束的执行，
  不体现在使用者身份。所有 ⏳ 触发的最终判据仍应来自用户本人的使用。
- 会话有写权限是**我的设计疏漏**（preset 自带 bash/fs 工具且 cwd 是仓库），不是产品缺陷本身；
  但它把"代理使用"变成了一次**真实的自主协作**，因此暴露了 F1/F2——合成探针永远测不到这类问题。
